## Epic 13 — Account Balance at a Point in Time (2026-10-02, reworked 2026-10-03)

Code Generation for the Database unit; see `database-account-balance-code-generation-plan.md` (its Steps 1 to 10, then the **REOPENED** section with steps R1 to R6) and `../functional-design/` (BR-30..BR-38). New enum `AccountType`; new entities `Account`, `AccountKey`, `BalanceAnchor`, `StatementAccount`.

**History, stated plainly**: the first version of this work (2026-10-02) put an account link and a closing balance on `BankStatement`, assuming one account per PDF. During the Ingestion Worker's Functional Design the user chose to handle PDFs that hold several accounts in this same feature, which reopened the schema. Migration 0019 was **reworked in place** (not followed by a 0020) because a read-only check showed the live database at migration 0018 with no `accounts` table, i.e. 0019 had only ever run in disposable test databases. The final shape is described by the rows above.

**Files**: Modified `database/src/transactagent_db/models.py`, `database/tests/test_models.py`, `database/migrations/versions/0001_initial_schema.py`. Created `database/migrations/versions/0019_account_balance.py`. `README.md` in this directory lists package contents generally, with no per-entity or per-migration list, so it needed no change.

**Tests**: 39 new example-based tests across `TestAccount`, `TestAccountKeyUniqueness`, `TestBalanceAnchor`, `TestStatementAccount` (BR-33, BR-37), `TestTransactionStatementAccount` (BR-38), and `TestAccountDeletionRestricted` (including the BR-36 wipe order); full suite **96/96** passing against a real PostgreSQL 16 (testcontainers). Property-based testing does not apply: this unit is declarative schema only, as noted at the top of `test_models.py`. `ruff check src tests` (the scope CI uses) clean.

**Migration 0019 live verification (43 checks, all passing)** against fresh disposable PostgreSQL containers, using a scratch virtualenv outside the repository (this unit's own `.venv` has a broken Python symlink, untouched):
- upgraded an **empty** database to 0018, seeded a representative category, statement, and transaction, upgraded to 0019: both rows preserved, the transaction's `statement_account_id` null, its amount unchanged, and **`bank_statements` unchanged**;
- inspected the **migrated** schema directly: the four new tables, `transactions.statement_account_id` (uuid, nullable), the composite foreign key as `FOREIGN KEY (bank_statement_id, statement_account_id) REFERENCES statement_accounts(bank_statement_id, id) ON DELETE RESTRICT`, BR-30 as `UNIQUE NULLS NOT DISTINCT`, BR-32, BR-33, BR-37, the target unique constraint, the index, the enum's lowercase labels, and every new foreign key `ON DELETE RESTRICT`;
- on the migrated database: a duplicate account on one statement, a closing balance without a date, and linking a transaction to **another statement's** section were each rejected by the named constraint; linking to its own statement's section was accepted; deleting a section that has a transaction, and an account that has a section, were rejected. (The live check labelled "deleting a statement that still has a section" was in fact blocked by the seeded transaction; the isolated case, a statement with only a section, is covered by the unit test `test_statement_with_a_section_cannot_be_deleted`.)
- a second `alembic upgrade head` was a safe no-op; `alembic downgrade 0018` removed the four tables, the column, and the enum type and left the seeded rows intact; re-upgrading succeeded;
- the whole chain also ran `upgrade head`, `downgrade base`, `upgrade head` on an empty database, leaving only `alembic_version` at base with no leftover enum.

**Two things live verification caught that the model-based test suite cannot see:**
1. **A fix to `0001_initial_schema.py` (found in the first version, extended for the reworked design).** Migration 0001 creates its tables from the *current* models, so on a fresh database `alembic upgrade head` failed at the very first migration once a table referenced a table that does not exist yet at that point in history. The same class of problem was fixed there for three other columns on 2026-08-21. 0001 now creates `accounts` and `statement_accounts` temporarily alongside the initial tables (because `transactions` has a composite foreign key to `statement_accounts`, which references `accounts`), drops `transactions.statement_account_id` (which also removes the composite foreign key and the column's index), then drops the two temporary tables and the enum type, so 0019 stays the single source of truth. Existing databases never rerun 0001, so only the build-from-empty path is affected. This is an addition to the approved plan's Step 5, recorded in `audit.md`.
2. **0019's downgrade left the `accounttype` enum type behind** after dropping the tables; it now drops it explicitly.

## Epic 14 — Probable Duplicate Statement Detection (2026-10-03)

Design: `aidlc-docs/construction/database/functional-design/` (BR-39..BR-52) and `aidlc-docs/construction/plans/database-probable-duplicate-code-generation-plan.md`. Migration `0020_probable_duplicates.py` (revision `0020`, down-revision `0019`). Purely additive: no existing column, row, or constraint is changed; the six new tables start empty. The feature ships with detection switched off, so nothing here changes what a normal ingestion run does.

**Constraints are declared on the models**, including the partial unique index (BR-45) and the byte-order CHECK (BR-43), so `create_all` and the migration produce the same schema and the unit tests exercise the real constraints. None of the six tables has a foreign key to `bank_statements`, `statement_accounts` or `transactions` (BR-50), so the backfill's wipe order and the removal order are unchanged.

**Unit tests (188 passing in total; 92 new, example-based, PBT does not apply to this unit).** Beyond the per-rule tests: a metadata-only guard (BR-51) computes every table with a foreign-key path, including a transitive one, to the three statement tables and asserts it equals exactly `recurring_payment_matches`, `categorization_disagreements`, `recategorization_proposals`, `recategorization_jobs` (deleted) and `ingestion_run_files` (detached); its message names the three places to update when a future feature adds a dependent, and a separate test proves the traversal follows transitive paths. **Mutation check**: removing, one at a time, the partial unique index, the rank bound, the run-file link CHECK, the single-row CHECK and the byte-order collation each made a test fail. The collation mutation initially *survived*, because the test container's default collation already is byte order; a test that reads the stored constraint definition and requires `COLLATE "C"` now catches it.

**Migration 0020 live verification (80 checks, all passing; re-run in full after the 2026-10-04 `removal_allowed` rework)** against fresh disposable PostgreSQL containers, using a scratch virtualenv outside the repository:
- *Existing database*: a database at 0019 whose outcome enum was rebuilt with its original three values (as a real database created before this feature has), seeded with a statement, transaction, and run files of each existing outcome, upgraded to 0020: every row preserved with a null comparison link, the enum gained exactly the new value, a `skipped_probable_duplicate` run file could then be inserted (which proves the value was committed before the CHECKs that mention it), all six tables and five new enum types exist with lowercase labels, every constraint and index exists, and every foreign key has its designed delete rule.
- *Constraints on the migrated database*: each of BR-42, BR-43, BR-45, BR-46, BR-48, BR-49 rejected a violating row by its named constraint; a failed job did not block a retry; a comparison referenced by a run file cannot be deleted; deleting a comparison deleted its rows.
- *Backup mechanism*: `to_jsonb` / `jsonb_populate_recordset`, the Backfill Tool's backup technique, round-tripped a removal job with its UUID array and JSONB columns.
- *Downgrade*: **refused with a clear message** while a `skipped_probable_duplicate` run file exists (nothing changed), and succeeded once those rows were gone: tables, column, both CHECKs and the five enum types removed, seeded rows intact; the added enum value remains (PostgreSQL cannot drop one, as in 0005); re-upgrade succeeded.
- *Idempotence and chains*: a second `upgrade head` was a no-op; empty database `upgrade head`, `downgrade base`, `upgrade head` succeeded and base left only `alembic_version` with no leftover Epic 13 or 14 enum; **0018 to head in a single Alembic run** succeeded (so the committed ADD VALUE works in the middle of a run); a database whose default collation is **not** byte order (ICU `en-US`, where `'a' < 'B'`) accepted `('B…', 'a…')` and rejected `('a…', 'C…')`, as Python's byte order does.
- *Drift*: `alembic check` reports exactly three items on the migrated schema and nothing from Epic 13 or 14: the older raw-SQL partial indexes for BR-10, BR-14 and BR-21, which migrations create and the models do not declare. This predates this work.

**Things verification found that the model-based tests cannot see:**
1. **A first version of the check was wrong, not the migration.** On a database built from empty, `0001` creates the outcome enum from the *current* model, so the new value is already there and 0020's `ADD VALUE IF NOT EXISTS` does nothing. An existing database lacks the value. The verification therefore rebuilds the enum as an existing database has it, which is the only way the committed `ADD VALUE` path is exercised.
2. **`0001_initial_schema.py` needed the same fresh-database fix as for Epic 13.** It now also creates `duplicate_comparisons` temporarily (because `ingestion_run_files`' current definition references it), drops the new column, drops the second CHECK **by name** (it names only existing columns, so dropping the column would have left it behind and 0020 would then have failed with "already exists"), and drops the temporary table.
3. The `outcome::text` fallback the plan reserved was **not needed**: `autocommit_block()` works under this project's `env.py`, including mid-run.

**Regression**: with the changed shared package, the existing Ingestion Worker suite (467) and API Service suite (261) pass unchanged. The API Service's own `.venv` points at a Python that no longer exists, so a scratch environment outside the repository was used for it; neither unit was edited.

## Contract for Units 2 and 3 — rules this unit deliberately does not enforce

The schema enforces BR-30 (account keys), BR-32's one-anchor rule, BR-33 (closing balance and date together), BR-37 (an account at most once per statement), BR-38 (a transaction's section belongs to its own statement), and the `RESTRICT` deletion rules. Everything else is an application-layer duty:

| Rule | Owner | What it requires |
|---|---|---|
| BR-31 | Unit 3 Account Resolver; Unit 2 Account Management | `Account.currency` never changes; every key of an account carries it; a merge is refused when currencies differ |
| BR-32 (future-date rule) | Unit 2 Account Management | reject an anchor whose `as_of_date` is in the future; offer no anchor for a non-deposit account; keep (but ignore) an anchor when an account stops being a deposit account |
| BR-34 | Unit 3 Account Resolver; Unit 2 Account Management | set `type_user_set` when the user corrects a type; never let an extraction change `account_type` once it is true |
| BR-35 (all-or-nothing, anchor choice, co-occurrence) | Unit 2 Account Management | one transaction: check currency **and that no statement lists both accounts**, settle the anchor, re-point the absorbed account's **statement sections** and keys, delete the emptied account last — the database refuses deleting an account that still has sections, keys, or an anchor |
| BR-36 | Unit 3 Backfill Tool | skip statements whose PDF is missing from Drive or that already have sections; wipe in foreign-key order after detaching `ingestion_run_files.bank_statement_id`: dependents of transactions, then `transactions`, then `statement_accounts`, then `bank_statements`; never touch `accounts`, `account_keys`, or `balance_anchors`; also remove the wiped transactions' vectors from the vector store (not a database concern) |
| New-ingestion duty (Scope Change) | Unit 3 Ingestion Worker | every statement ingested after this feature gets one `statement_accounts` row per distinct account, and every transaction gets its section's id (`transactions.statement_account_id` is nullable only for pre-backfill data); the Account Resolver collapses same-account sections before anything is stored, so BR-37 is only a backstop |

Because the relationships on `Account` and `BankStatement` that point at `statement_accounts` use `passive_deletes="all"`, a plain `session.delete(...)` in Unit 2 or 3 will not null or cascade children; it will raise an `IntegrityError` if any child remains, which is the intended behavior. `Transaction` deliberately has **no** ORM relationship to `StatementAccount` (the composite foreign key would overlap the existing `bank_statement` relationship); Units 2 and 3 join explicitly on `Transaction.statement_account_id == StatementAccount.id`.

### Epic 14 additions to the contract (2026-10-03)

The schema enforces BR-39 (one record per hash), BR-40 (evidence always present), BR-42 (comparison bounds), BR-43 (pair order and uniqueness), BR-45 (one active job per pair), the CHECK halves of BR-46, BR-48 (single scan row), BR-49 (run-file link), and the `RESTRICT` / `CASCADE` rules. Everything else is a duty of Units 2 and 3:

| Rule | Owner | What it requires |
|---|---|---|
| BR-41 | Unit 2 Duplicate Review (override); Unit 3 Probable Duplicate Detector, Statement Removal Handler, Backfill Tool (the other writers) | insert a `KnownFile` as `probable_duplicate` or `confirmed_duplicate`; the only later change is to `overridden` (from either), which stamps `decided_at`; `overridden` is final. A `probable_duplicate` is never re-evaluated by a later run |
| BR-42 (write-once) | Units 2 and 3 | never update a comparison or its rows after insert; the API displays the stored snapshot and never recomputes the keep-proposal |
| BR-44 | Unit 3 Probable Duplicate Detector | insert a pair only when no row exists for those two hashes; refresh a `pending` pair; mark a `pending` pair `superseded` when its statements are no longer both held; `dismissed`, `removed`, `superseded` are final; exclude files whose `KnownFile` is `overridden` |
| BR-46 (ordering) | Unit 3 Statement Removal Handler | delete the statement, sections, transactions and dependents **and** set `embeddings_pending` with `removed_transaction_ids` in **one** transaction; only then delete embeddings and set `completed`; bound the retries and park the job as `embeddings_failed` |
| BR-47 | Units 2 and 3 | never delete a removal job after it finishes |
| BR-51 | Units 2 and 3 | use the one dependents list (see the guard test) for the removal's deletes, the backfill's wipe order, and the API's removal preview; the guard test fails if a table is added that none of them knows |
| BR-52 | Unit 3 Ingestion Orchestrator | count a probable-duplicate skip in `files_skipped_count`; never `completed_with_failures` because of one |
| BR-36 (Epic 14 addendum) | Unit 3 Backfill Tool | never wipe or detach the six new tables; include them in the backup and restore set; add `KnownFile` rows for pre-registered skips; mark pending pairs it resolves `superseded`; honour `dismissed` pairs |
| BR-53 | Unit 3 Probable Duplicate Detector (writes `removal_allowed`); Unit 2 Duplicate Review (reads it) | true only when the smaller statement has at least `duplicate_match_ratio` times the larger one's transactions; computed and refreshed by every scan; the API displays it, refuses to create a removal job when it is false, and never recomputes it; the Statement Removal Handler re-verifies it |
| Python-side defaults | Units 2 and 3 | like every earlier table in this module, defaults such as a pair's `pending`, a job's `queued` and zero counts are applied by the ORM, not by the database. Raw SQL inserts must supply them |
| Consumers of the new outcome | Unit 4 Frontend | `frontend/src/api/types.ts` has `RunFileOutcome` as a closed union and needs `"skipped_probable_duplicate"` |
