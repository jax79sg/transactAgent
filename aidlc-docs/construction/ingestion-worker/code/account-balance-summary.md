# Account Balance at a Point in Time (Epic 13) — Ingestion Worker Code Summary

Code Generation for the Ingestion Worker Service. Design: `../functional-design/` (WR-44..WR-56) and the plan `../../plans/ingestion-worker-account-balance-code-generation-plan.md`. Stories: US-13.1 (accounts from statements, several per PDF), US-13.6 (closing-balance capture), US-13.7 (the backfill).

## What was built

| Area | Files | What it does |
|---|---|---|
| Extraction contract | `extraction/schemas.py`, `prompts.py`, `service.py` (modified) | A statement holds **account sections** (identifier as printed, account type, currency, closing balance and date, transactions). Parsing is lenient: a flat reply is wrapped as one section; an unknown type, malformed balance, or malformed date degrades to unknown/absent and **never fails an extraction**. Existing safeguards kept: whole-document day/month swap, per-section chronological correction, balance-line exclusion, future-date drop, WR-2, zero-transactions (now across the whole statement), confidence gate. Closing balances get date validation with a fallback to the validated statement date, else the pair is dropped (WR-47). |
| Account Resolver | `accounts/normalize.py`, `repository.py`, `service.py` (new) | Pure normalization (`bank_key`, identifier, default name) and `resolve_sections`: key lookup or create, same-account sections collapsed, type rules, run-log lines. |
| Recording | `duplicate_detection/service.py` (modified) | `record_statement_accounts`: one `StatementAccount` per resolved section, carrying the closing balance. |
| Pipeline | `orchestrator/pipeline.py` (modified) | Resolve sections, record the statement and its sections, convert each transaction with **its section's currency**, one classification batch per file, persist each transaction with its section id. **A savepoint around each file** (see below). |
| Vector store / Drive | `embedding/vector_store.py`, `clients/drive_client.py` (modified) | `recreate_transactions_collection()`, `ensure_subfolder()`. |
| Backfill Tool | `backfill/` (new): `tables.py`, `export.py`, `service.py`, `corrections.py`, `restore.py`, `report.py`, `check_extraction.py`, `__main__.py` | `check-extraction` (read-only), `run`, `finish`, `restore`. |

## Deviations and refinements from the Functional Design (stated plainly)

1. **A savepoint per file, not a plain rollback** (a found gap, not a design change). Before this work, a file's writes were only flushed and `fail_run()` *committed*, so a file that failed unexpectedly had its half-written statement committed with the run's failed status, and its recorded content hash made it be skipped as a duplicate forever. A plain `db.rollback()` was tried first and would have discarded the whole outer transaction in tests; a SAVEPOINT around each file discards only the file in flight. A test proves it: with the savepoint removed, the test fails with an orphan account left behind.
2. **Closing-balance dates never trigger the whole-document day/month swap** (refines WR-46). Only transaction dates are evidence; a closing date follows the swap when transactions trigger it. Reason: one odd closing date must not be able to corrupt transaction dates that are otherwise correct.
3. **Excluded-line anchoring stays per section** (a limitation of WR-46). The existing `_correct_ambiguous_transaction_dates` helper keeps its signature (an existing test patches it), so for a multi-section PDF the statement-date anchor for administrative lines is validated against each section's own latest date, not the whole document's. For single-section PDFs (the usual case) behavior is identical to before.
4. **The completion report identifies what the backfill produced by id, not by timestamp** (refines WR-56). The backup lists every pre-existing statement and run-file, so anything not in it is new; this is exact and does not depend on the tool's clock agreeing with the database's. Found because the end-to-end test exposed the timestamp approach as fragile.
5. **After recreating the vector collection, *every* remaining transaction is queued for re-embedding** (generalizes WR-52, which said "kept statements"). The recreated collection is empty, so any transaction that still exists, including statements already converted in an earlier run, has lost its vector.
6. **15 raw bank names become 11 keys, not 10.** The earlier documents miscounted; the 11 listed keys were always correct, and the count is now fixed everywhere (Functional Design, plans) and asserted in a test.
7. **Backup export uses the database's own `to_jsonb(row)` / `jsonb_populate_recordset`**, so every column round-trips exactly with no hand-written type conversion (a plan addition). A restore round-trip test proves the tables come back identical.
8. **New read-only `check-extraction` command** (a plan addition, serving NFR-AB-3 and answering "which of my PDFs are multi-account" before anything is wiped).

## Duplicate statements: what is and is not recognized (asked by the user, 2026-10-03)

- **Recognized: byte-identical PDFs.** Duplicate detection is a SHA-256 of the file's raw bytes (`duplicate_detection/service.py`). A second Drive file with exactly the same bytes, whatever its name or Drive id, is skipped (`skipped_duplicate`) and creates no statement, account section, or transaction. In the live data this has fired: 3 Drive files were byte-identical copies of already-ingested statements (10 skip events across runs), and all 172 statements have distinct hashes. The Backfill Tool inherits this: the reingest skips identical copies the same way, and the completion report now lists them under "Byte-identical copies skipped as duplicates" instead of wrongly calling them "not ingested yet" (a defect found while answering this question, fixed with a test).
- **Not recognized: the same statement as a different file.** Anything that changes the bytes defeats the hash: downloading the same statement twice from the bank (PDF metadata or timestamps differ), a re-export, a scan, a print-to-PDF, removing a password. **There is no transaction-level or period-overlap check anywhere in the worker**, before or after this work. Two such files are ingested as two statements and their transactions are counted twice.
- **Evidence in the live data (read-only, 2026-10-03)**: two UOB statements, each with 5 transactions dated 2026-06-02 to 2026-06-30, and **all 5 transactions identical** (date, description, amount). That is almost certainly one June statement ingested twice from non-identical files; those 5 transactions are double-counted today in the dashboards. Six transaction keys in total appear in more than one statement; this pair accounts for the only sizeable overlap.
- **Effect on the balance feature**: an unrecognized duplicate in a deposit account would double-count its transactions in that account's balance. The closing-balance cross-check (US-13.6) would raise a discrepancy warning *if* the account has an anchor and the statements printed closing balances, which is the safety net, but nothing prevents the duplicate itself.
- **The Backfill Tool does not remove such duplicates**: both files have different hashes, so the reingest recreates both. `check-extraction` and the completion report do not yet flag probable duplicates (same bank and account, same period, mostly the same transactions).

## What was NOT verified (so it is not assumed)

- Nothing has been run against the **live database, your real Drive, the real Qdrant, or Gemini**. The extraction prompt's new sections shape has therefore **not yet been tried on a real statement**; that is exactly what `check-extraction` is for, and it is the first thing Build and Test should do (with your go-ahead).
- Qdrant's delete-and-create calls are exercised only against a mock client.
- The `cmd_*` command wrappers around `session_scope()` (which connect through the worker's own engine) are covered through their parts and the parser, not as a whole, because they need the real service environment.
- Resuming after the worker is *restarted* mid-reingest: worker startup recovery fails any run left `running`, which fails the backfill's run. The normal fallback applies (see the runbook), but this exact sequence is documented, not tested.

## Operator runbook (for the real run, later, with your explicit go-ahead)

All commands run through `docker compose` from the project root. **Stop the worker first** so its background work (embedding batches, nightly backup) cannot interleave, and **do not restart it until the reingest has finished** — worker startup recovery marks any run left `running` as failed.

1. **Look first, change nothing**: `docker compose stop ingestion-worker`, then
   `docker compose run --rm ingestion-worker python -m ingestion_worker.backfill check-extraction --limit 10`
   Compares the new extraction with what is stored for a sample spread across banks, and lists every multi-account PDF it sees. It writes nothing but calls Gemini once per PDF. Use `--all` to check every statement (172 Gemini calls). Do not go on if mismatches look wrong.
2. **The real run**: `docker compose run --rm ingestion-worker python -m ingestion_worker.backfill run`
   It refuses if any run or job is active, Drive or the vector store is unreachable, or there is no user. It prints the dry run, takes and **verifies** the backup (printing the Drive folder name, `pre-backfill-<UTC timestamp>`), then asks you to type exactly `WIPE <n> STATEMENTS`. Anything else changes nothing. After that it wipes, recreates the vector collection, and reingests every PDF; this takes as long as the original ingestion and uses proportionate Gemini and categorization quota.
3. **Finish**: `docker compose run --rm ingestion-worker python -m ingestion_worker.backfill finish --backup pre-backfill-<timestamp>`
   Re-applies the manual corrections from the backup, writes the completion report (printed, and saved as `completion-report.txt` and `.json` in the same Drive folder). Safe to run twice.
4. **Start the worker again**: `docker compose start ingestion-worker`. It re-embeds every transaction in the background.
5. **If the reingest is interrupted** (a crash, a closed terminal): run step 2 again; there is nothing left to wipe, so it goes straight to the reingest of the missing PDFs with no second backup. Or, with the worker running, use the app's normal "run ingestion". Then run `finish` with the **original** backup name.
6. **To undo** (before ingesting anything new that you care about): `docker compose run --rm ingestion-worker python -m ingestion_worker.backfill restore --backup pre-backfill-<timestamp>`, typing `RESTORE FROM <folder name>` when asked. It verifies the backup against its manifest first, replaces the backed-up tables in one transaction, and queues every transaction for re-embedding. Anything changed in those tables since the backup is lost.

## Refinement made before the real run (2026-10-05)

`check-extraction` on 10 real statements found 3 mismatches. Two (OCBC) were ordinary OCR variance between model runs. The third (MariBank) differed on all 52 transactions **only by line breaks** where the stored text has spaces. Because `finish` re-attached manual corrections by exact description, that alone would have lost every correction on such statements (the user has 810, 66 on MariBank). `backfill/corrections.py` now compares descriptions with whitespace collapsed (both sides; 142 stored descriptions contain a line break) and adds a strict, reported fallback (one leftover correction and one free row in the same statement, date, amount and direction; never over a different manual correction). On a real 3-statement sample the re-attached share rose from 9 to 15 of 16. Ten new tests (the worker suite is now 674), eight mutations each caught (the first run of the mutation check found a real gap — a stored description with its own line break — and a test was added). The completion report gains a "placed by date and amount" section. WR-55 carries the dated refinement.
