# Business Rules — Unit 3: Ingestion Worker Service

## WR-1: Extraction Failure Criteria
A statement MUST be flagged `failed` (not committed) if ANY of: (a) the extraction LLM call errors out (no cross-provider retry, Clarification 1b); (b) the response fails structural/schema validation; (c) zero transactions are extracted from a non-trivially-short statement; (d) the LLM's self-reported confidence is below the configured threshold. **Traces to**: FR-2.5, US-1.3 edge case.

## WR-2: Bank/Currency Must Be Identified to Commit
A statement's extracted transactions MUST NOT be committed unless the extraction step identified both a bank name and a currency for the statement; failure to identify either is treated as an extraction failure (WR-1c, structural incompleteness). **Traces to**: FR-2.3, FR-2.4.

## WR-3: Similarity Threshold and Manual Precedence
A similarity match is only used as precedent if it clears a minimum fuzzy-match score (a configured threshold, tuned during Code Generation/testing — not hardcoded to an arbitrary number here). Among matches clearing the threshold, any `category_source='manual'` match is preferred over `similarity`/`llm`-sourced matches regardless of relative fuzzy score (FR-5.3). **Traces to**: FR-5.2 step 1, FR-5.3.

## WR-4: LLM Categorization Constrained to Whitelist
The categorization LLM call MUST be constrained (structured output / enum) to return only a whitelist category name or the literal "UNSURE"; any other value, or a call failure, results in `UNSURE` being assigned — never a free-text or invalid category value reaching the database (which BR-1 in Unit 1 would reject anyway, but this rule ensures it's handled gracefully at this layer rather than crashing the pipeline). **Traces to**: FR-5.1, FR-5.2 step 4.

## WR-5: Retroactive Recategorization Uses Similarity Only
The FR-5.4 retroactive re-scan (triggered by a manual correction) MUST only use the Similarity Matcher against the newly-corrected transaction — it MUST NOT make an LLM call. Updated transactions get `category_source = 'similarity'`, not `'manual'` (see business-logic-model.md note). **Traces to**: FR-5.4.

## WR-6: Currency Conversion Source Priority
For each transaction, the converted SGD amount MUST be resolved in this order: (1) statement-printed SGD amount if the extraction step captured one, (2) the transaction's own amount if `currency = 'SGD'` already (trivial identity, no lookup), (3) a cached or freshly-fetched `exchangerate.host` historical rate for the transaction's date, (4) the nearest prior date's rate (marked approximate) if the exact date is unavailable, (5) `conversion_unavailable = true` if none of the above succeed. **Traces to**: FR-10.3, FR-10.5, Clarification 2a/2b.

## WR-7: No Silent Retry Across Providers
Neither the extraction (Gemini) nor categorization (OpenRouter) LLM calls retry against a different provider on failure (Clarification 1b = B) — a failure at either step is terminal for that statement/transaction within the current run, surfaced via WR-1 (extraction) or WR-4 (categorization) rather than silently attempted elsewhere.

## WR-8: Single Active Run Respected at the Worker Level Too
Although AR-6 (Unit 2) already prevents a second run from being *enqueued* while one is active, the Ingestion Orchestrator MUST also never concurrently process two runs itself (its polling loop claims and fully completes one run before polling for the next) — a defense-in-depth measure, not a duplicate of AR-6.

## WR-9: Recategorization Search Is Broadened, Still Similarity-Only (added 2026-08-02 — Epic 6)
The retroactive re-scan (FR-5.4, WR-5) is broadened to search two candidate buckets against the corrected transaction — `UNSURE` transactions (as before) and already-categorized transactions (`category_source IN ('manual', 'similarity', 'llm')`) whose current category differs from the correction. WR-5's constraint still holds for both buckets: similarity matching only, no LLM call. A match is split into two outcomes by score: `UNSURE`-bucket matches at or above a new, higher **auto-apply threshold** are applied immediately exactly as WR-5 already specified (`category_source = 'similarity'`); every other match — `UNSURE`-bucket matches at or above the existing similarity threshold (WR-3) but below the auto-apply threshold, and *all* already-categorized-bucket matches regardless of score — creates a `RecategorizationProposal` row with `status = 'pending'` instead of writing to `transactions`. **Traces to**: FR-RR-1, FR-RR-2, FR-RR-3, US-6.1, US-6.2.

**Revised (2026-08-19 — Recategorization Scope Narrowing, see `recategorization-scope-narrowing-requirements.md`)**: The already-categorized bucket this rule added is **removed entirely**, not narrowed to a substitute bucket. The retroactive re-scan searches `UNSURE` transactions only, exactly as it did before WR-9 originally broadened it (i.e., reverting to WR-5's original single-bucket scope). Reason: the already-categorized bucket's match accuracy was observed by the user to be low in practice, and unlike the `UNSURE` bucket (which only ever affects transactions with no confident category yet), a wrong match here could silently suggest overwriting a transaction that already has a *correct*, human-or-high-confidence-assigned category — a materially worse failure mode than a wrong `UNSURE` suggestion. `RecategorizationProposalSourceBucket.CATEGORIZED` remains a valid enum value (Database) since existing historical rows use it and are explicitly left as-is (not backfilled or cleared) — only its *production* stops.

## WR-10: Already-Categorized Matches Never Auto-Apply (added 2026-08-02 — Epic 6; bucket removed 2026-08-19, see WR-9's revision note)
A match against an already-categorized transaction (the bucket added by WR-9) is recorded as a `pending` proposal regardless of how high its similarity score is — the auto-apply threshold in WR-9 applies only to the `UNSURE` bucket. A candidate already assigned the exact category being proposed is skipped entirely (not proposed against itself, a no-op change).

**Status**: This rule is now moot going forward — its bucket no longer exists (WR-9's revision). Kept in the document rather than deleted, since it correctly describes the (still-valid, unreviewed) historical `pending`/`categorized` proposals that predate this change. **Traces to**: FR-RR-4, US-6.3.

## WR-11: Backup Due Determination (added 2026-08-08 — Epic 7)
A backup attempt is due when both are true: (a) the current time is at or past today's configured nightly schedule time, and (b) no `BackupRun` row exists yet for today's calendar date. This single check, evaluated on every poll cycle, is both the normal nightly trigger and the FR-8 catch-up trigger — a worker that was offline at the scheduled time satisfies condition (a) as soon as it's back online, with no separate startup/catch-up code path needed. **Traces to**: FR-1, FR-2, FR-8.

## WR-12: Every Attempt Records Exactly One Outcome (added 2026-08-08 — Epic 7)
`runBackup()` MUST catch every exception internally and MUST always write exactly one `BackupRun` row (BR-17, Unit 1) before returning — no exception may propagate out uncaught. This is the actual enforcement mechanism for FR-9's no-same-night-retry rule: without a written row, WR-11's due-check would keep returning true on every subsequent poll cycle for the rest of the day, causing a silent retry storm. **Traces to**: FR-9.

## WR-13: CSV Snapshot Content (added 2026-08-08 — Epic 7)
Each backup attempt exports a full snapshot of every row currently in `transactions`, with all columns as stored (per FR-6's documented assumption: raw columns/foreign-key IDs, not human-readable joins) — never an incremental/delta export. **Traces to**: FR-1, FR-6.

## WR-14: Backup Folder Resolution and Retention Scope (added 2026-08-08 — Epic 7)
Backup uploads and retention operate exclusively within the `backup` subfolder of the dedicated backup Drive folder (a separate config value from the ingestion source folder, per FR-3/FR-4) — never the ingestion source folder itself. The subfolder is created if it doesn't already exist (idempotent check, every attempt). Retention (`enforceRetention`) only ever considers files whose name matches this feature's own naming convention (`transactions-backup-*.csv`) — a file that doesn't match is never a deletion candidate, even if it's the oldest file present (NFR-4). **Traces to**: FR-3, FR-4, FR-7, NFR-4.

## WR-15: Failure Classification (added 2026-08-08 — Epic 7)
A failed attempt's `failure_category` is `drive_connectivity` if the failure originated from `DriveNotConnectedError`, `DriveReauthRequiredError`, or a Drive-API `TransientError`/`HttpError` raised by any of `ensureBackupFolderExists`/`uploadFile`/`listBackupFolderFiles`/`deleteFile`; every other exception (e.g. a database error while querying transactions for the export) is classified `other`. **Traces to**: FR-10, FR-11.

## WR-16: Recurring Payment Match Trigger and Candidate Selection (added 2026-08-08 — Epic 8)
Immediately after a transaction is persisted (inside `_persist_transaction`, not a separate pass), the Recurring Payment Manager searches `RecurringPayment` rows with no existing "live" match (BR-21: `pending`/`approved`/`auto_applied`) for the relevant cycle, whose due-date window covers the transaction's date, and whose description/category clears the existing similarity threshold (reusing the Categorization Engine's matcher, NFR-1) against the payment's name. The payment's `expected_amount` is a loose guide only (FR-5) — never a hard filter on whether a candidate is considered at all. **Traces to**: FR-5.

## WR-17: Cycle Period Derivation (added 2026-08-08 — Epic 8)
When a transaction's date could plausibly belong to either of two adjacent due-date instances (the matching window spans a month/year boundary), the instance used is whichever is numerically closer to the transaction's date by day distance. `cycle_period` (`"YYYY-MM"` for monthly, `"YYYY"` for annual) is derived from that chosen instance's month/year — never from the transaction's own calendar month directly. **Traces to**: FR-5, BR-21.

## WR-18: Trust/Tolerance Auto-Apply Decision (added 2026-08-08 — Epic 8)
A match against a `RecurringPayment` with `is_trusted = false` is always created as `pending` (FR-6), regardless of amount closeness. A match against a `RecurringPayment` with `is_trusted = true` is created as `auto_applied` only when the transaction's amount is within tolerance of `expected_amount` — reusing the same dual-gate shape already established for similarity-based amount checks elsewhere in this unit (a percentage tolerance, OR an absolute floor for small amounts) — otherwise it still falls back to `pending`, exactly as a never-trusted payment would (FR-7). Exact tolerance/floor values are tuned during Code Generation, not hardcoded here (NFR-3, same precedent as WR-3). **Traces to**: FR-7.

## WR-19: Detection Scan Cadence and Pattern Criteria (added 2026-08-08 — Epic 8)
The detection scan (checked as `poll_once()`'s fourth branch, `services.md`) runs at most once per configured interval (e.g. daily — exact cadence tuned at Code Generation). It considers only **monthly-cadence** patterns (FR-12: annual-cadence detection is out of scope for this version) — transactions with similar description/category and amount recurring roughly every ~30 days (a day-distance tolerance, tuned at Code Generation), appearing 2 or more times, not already covered by an existing `RecurringPayment`'s recent matches, and not already represented by a `DetectionSuggestion` row (BR-22 is the uniqueness backstop; the scan should still avoid attempting a doomed insert where practical). **Traces to**: FR-12, FR-13.

## WR-20: Reference-Code Noise Normalization Before Text Scoring (added 2026-08-11 — Similarity-Matching fix)
Before `find_best_match` computes `token_sort_ratio` between a description and any candidate, both sides
MUST be passed through a new, standalone `normalize_reference_noise` function (scoped to `similarity.py`
only — not shared with `recurring_payments/service.py`'s unrelated `_normalize_description`, FR-5). The
function strips two token shapes, word-bounded, in this order: (1) whole tokens of 3+ consecutive digits
(e.g. a PayNow reference number); (2) whole tokens 1–12 characters long containing at least one letter AND
at least one digit (e.g. a QR code fragment). Whitespace is then collapsed. Payee/merchant text itself is
never altered by this rule — only tokens matching one of the two shapes above are removed (FR-3). The
amount-range gate (`amounts_in_range`) is unaffected and remains the primary defense against same-text,
different-amount false positives (NFR-2) — it is applied independently of, and before, text scoring.
**Known, accepted limitation**: a genuine merchant/payee name that happens to itself be a short letter+digit
token (e.g. a hypothetical `3M`) would also be stripped by rule (2) above — an explicit trade-off of the
conservative-but-general heuristic (FR-2), not a defect. **Traces to**: FR-1, FR-2, FR-3, FR-4, FR-5.

## WR-21: Embedding-First-Then-Fuzzy-Fallback Decision Order (added 2026-08-12, scope corrected 2026-08-13 during Code Generation — Local Embedding-Based Semantic Similarity, Epic 9)
At three of this unit's candidate-search call sites — Categorization Engine's `findSimilarPastTransaction` (FR-4) and `findRecategorizationCandidates` (FR-4), and Recurring Payment Manager's `matchNewTransaction` (FR-4) — candidate search follows this fixed order: (1) compute a transient, non-persisted query embedding of the relevant raw text via `Embedding Manager.computeEmbedding()` (WR-24: unnormalized, FR-9); (2) if that succeeds, query the Vector Store Client for the appropriate collection (WR-22), excluding the source entity itself via `filters.excludeEntityId` whenever the query subject is itself a stored candidate (the retroactive re-scan's source transaction); then apply WR-23's filtering (`findSimilarPastTransaction`/`findRecategorizationCandidates`) or collect every clearing candidate ID (`matchNewTransaction`, which then still applies its own due-date-window/live-match checks per candidate, WR-16); (3) if a surviving candidate is found, use it exactly as a fuzzy-text match would be used today (FR-5) — no separate, parallel decision path; (4) otherwise (embedding computation failed per FR-10, the endpoint/vector store is unreachable, or no candidate survives filtering), fall through to the existing fuzzy-text `find_best_match`/`token_sort_ratio` check (with WR-20's normalization, where applicable) completely unchanged — a whole-operation fallback (every remaining candidate gets checked via fuzzy-text), not a per-candidate one. This is a single ordered chain, not two independent attempts — the fuzzy-text path is only ever reached once the embedding path has already been tried and found nothing usable.

**`runDetectionScan` does not follow this chain** — see WR-22's correction: it has no existing fuzzy-text search to fall back to (its own mechanism, WR-19, is exact-normalized-description grouping), so its embedding step is a separate, purely additive group-merge pass, not an instance of this rule. **Traces to**: FR-3, FR-4, FR-5.

## WR-22: Candidate Collection Targeting Per Call Site (added 2026-08-12, corrected 2026-08-13 during Code Generation — Epic 9)
The Vector Store Client's `collection` parameter (WR-21 step 2) is chosen per call site, not uniformly: `findSimilarPastTransaction`/`findRecategorizationCandidates` (Categorization Engine) target `collection='transactions'` — comparing a description against *other transaction descriptions*. `matchNewTransaction` targets `collection='recurring_payment_names'` — it alone compares a transaction's description against `RecurringPayment.name` values. **Correction to Application Design**: `component-methods.md`'s original Epic 9 addendum stated both Recurring Payment Manager methods query `recurring_payment_names`; that conflated `matchNewTransaction`'s actual target with `runDetectionScan`'s, whose own grouping step (WR-19, unchanged) has no `RecurringPayment` in the loop until its later already-covered exclusion check, which is a DB join against `RecurringPaymentMatch`, not a vector search.

**Further correction (2026-08-13, discovered writing the actual grouping code)**: `runDetectionScan` does not use the Vector Store Client / `queryNearestNeighbors` at all, and its embedding step is not part of the WR-21 four-step chain the way the other three call sites are. Reading the real, already-shipped WR-19 implementation showed its grouping is **exact-normalized-description dict-key matching** (`_normalize_description` + a hash grouping), not a call to `find_best_match` — there was no existing fuzzy-text search in this call site for an embedding step to go "before." Instead: the exact-match grouping stays the primary, unchanged mechanism (WR-19), and a separate, purely additive pass (`_merge_groups_via_embedding`) merges two distinct groups when their most-recent transactions' embeddings (transient, query-time — computed via `computeEmbedding`, not read back from the vector store) clear the embedding-similarity threshold via direct `cosine_similarity`, not a vector-store search — the candidate pool is the small number of *distinct patterns* found that scan (personal-scale: dozens), not the full transaction history, so an in-memory pairwise comparison is simpler and cheap enough. **No fuzzy-text fallback exists for this merge pass specifically** (unlike the other three call sites' WR-21 step 4): when a representative's embedding is unavailable, the two groups simply stay unmerged, exactly as WR-19 already behaved before this feature — the exact-match grouping IS the pre-existing baseline this pass enhances, not something needing its own separate fallback. **Traces to**: FR-3, FR-4, WR-19.

## WR-23: Amount-Gate and Manual-Precedence Carryover, Bounded Top-K Selection, Score Rescaling (added 2026-08-12, extended 2026-08-13 during Code Generation — Epic 9)
An embedding-found candidate is subject to exactly the same checks a fuzzy-text-found candidate already is (NFR-1, FR-5) — the amount-range gate (`amounts_in_range`) and, where applicable (Categorization Engine only), the manual-source-precedence rule (WR-3) — never a separate or weaker check. Because `queryNearestNeighbors` returns a bounded top-K of nearest neighbors by raw cosine distance (K deferred to NFR Requirements/Code Generation, same precedent as `similarity_threshold`'s exact value), and the single nearest neighbor is not guaranteed to be the one that passes these checks, the Worker fetches the K candidates' full rows, keeps those clearing both the embedding-similarity threshold and the amount gate, and applies WR-3's manual-precedence rule among that eligible set (shared selection logic, `select_best_match`, factored out so the fuzzy and embedding paths apply it identically) rather than always taking the single nearest neighbor; if none of the K pass, this is treated identically to "no embedding candidate found" (WR-21 step 4) — falling through to fuzzy-text, never returning a worse-passing embedding candidate.

**Score rescaling (found necessary during Code Generation)**: cosine similarity (0.0-1.0) and fuzzy `token_sort_ratio` (0-100) are different scales, but a `SimilarityMatch.score` produced by either path is compared against and stored alongside fuzzy-scale values elsewhere in this codebase (`recategorization_auto_apply_threshold`, `RecategorizationProposal.match_score`) — feeding a raw 0.0-1.0 value into those comparisons would mean an embedding-sourced match could never clear a fuzzy-scale threshold like `recategorization_auto_apply_threshold` (97.0). An embedding-found candidate's `.score` is therefore rescaled (`cosine_similarity * 100`) once eligibility against `embedding_similarity_threshold` (the raw 0.0-1.0 value) has already been decided — every downstream consumer of `.score` sees the same 0-100 scale regardless of which path found the candidate. **Traces to**: FR-5, NFR-1.

## WR-24: Raw Text Fed to the Embedder (added 2026-08-12 — Epic 9)
Both the transient query-time embedding (WR-21 step 1) and the persisted storage-time embedding (`processNextEmbeddingBatch`, WR-26) are computed from the raw, unmodified text (a transaction's `description`, or a `RecurringPayment`'s `name`) — WR-20's `normalize_reference_noise` function is never applied before embedding (FR-9). WR-20's normalization remains scoped exactly as shipped: only within the fuzzy-text fallback path (`find_best_match`), unaffected by this feature. **Traces to**: FR-9.

## WR-25: Soft-Fail on Any Embedding-Path Failure (added 2026-08-12 — Epic 9)
A failure anywhere in the embedding path — the oMLX endpoint unreachable/erroring, the vector store unreachable/erroring — MUST NOT raise or propagate out of any of the four call sites (WR-21), MUST NOT fail or block statement ingestion, categorization, recurring-payment matching, or detection scanning, and MUST NOT leave any partial/inconsistent write (see WR-26 for the batch-write ordering that makes this safe). The affected call simply falls through to the fuzzy-text path (WR-21 step 4) exactly as if no embedding candidate had been found. This is a hard requirement, not a best-effort one — matches this project's established pattern of treating optional/enhancement paths (e.g. FX conversion's `conversion_unavailable`) as never blocking the primary workflow. **Traces to**: FR-10.

## WR-26: Embedding Batch Processing Mechanics (added 2026-08-12 — Epic 9)
`processNextEmbeddingBatch()` (the fifth `poll_once()` branch, `services.md`) selects a bounded batch (size deferred to NFR Requirements/Code Generation) of `pending`-status rows across both `Transaction` and `RecurringPayment` (`services.md` correction, Database `BR-25`), processed in ascending `created_at`/`id` order per entity type so an interrupted-and-resumed batch (NFR-4) always makes visible forward progress rather than reprocessing an arbitrary subset. For each row: call `Embedding Manager.computeEmbedding()` with the raw text (WR-24); on success, call `Vector Store Client.upsertEmbedding()` (idempotent — the same entity ID always overwrites its own prior vector) *before* flipping the row's `embedding_status` to `completed` — this ordering is what makes a crash between the two steps safe (WR-25): the row is simply left `pending` and reprocessed next cycle, re-upserting the same vector with no duplication. On an endpoint-unavailable error, the batch stops early for that cycle rather than burning through every remaining row on doomed calls (FR-10) — already-`completed` rows from earlier in the same batch are unaffected. This single mechanism is simultaneously "the async embedding job" for newly-created rows (FR-6, and `RecurringPayment` creates/renames per Database `BR-25`) and "the one-time historical backfill" for pre-existing rows (FR-11) — no separate code path or flag distinguishes them. **Traces to**: FR-6, FR-11, NFR-4.

## WR-27: Always-On, Batched, Concurrent LLM Classification (added 2026-08-16, revised 2026-08-16 during Build and Test — Matching Precision Refinement)
The LLM classification step (`classifyBatch`, Application Design Key Design Resolution 2) runs once per file, for every raw transaction extracted from that file, immediately after extraction succeeds and before the existing per-transaction persistence loop begins — not as a per-transaction last resort inside `categorize()` (superseding WR-4's "fallback" framing: the LLM still returns `UNSURE` on any failure per WR-4's existing contract, but it is no longer called *only* when similarity fails). A file with zero transactions extracted is a no-op (nothing to classify).

**Revision (found during this feature's own Build and Test, live-testing against the user's real local model server)**: the original version of this rule had each de-duplicated description as its own HTTP call, concurrency-bounded. Live testing showed a large statement would fire many simultaneous HTTP requests at a single local model server — exactly the load-concern this rule exists to manage, just via the wrong lever. Two-phase design instead:
1. **Batch phase**: de-duplicated descriptions are grouped into chunks of `llm_classification_batch_size` (env-configurable, default 10); each chunk is classified in a single prompt asking for a JSON array of category names, one per description, in order. Chunks run concurrently, bounded by `llm_classification_concurrency` (env-configurable, default 5, NFR-MPR-1) via a thread pool.
2. **Fallback phase**: any description the batch phase didn't return a validated answer for (the batch's response was unparseable, too short, or that specific entry wasn't a whitelist name/`UNSURE`) is classified individually via the original single-description call — also concurrent, also bounded by the same cap. Only the specific failed descriptions redo work, not every description in the batch they were part of.

The database session itself is never touched concurrently in either phase, only the whitelist lookup (once, upfront) and the LLM HTTP calls are. Live-verified against the real running oMLX server: a 6-description batch returned a fully valid JSON array in 1.04s (including a correct `UNSURE` for a deliberately ambiguous description); a 12-description `classify_batch` call (chunked into batches of 10 and 2, using the real live category whitelist) completed in 2.52s, all 12 correctly classified. **Traces to**: FR-MPR-1, FR-MPR-2, FR-MPR-3 (revised).

## WR-28: `categorize()` Decision Logic With the Always-On LLM Signal (added 2026-08-16 — Matching Precision Refinement)
`categorize()` now takes the already-known LLM classification (WR-27) as a parameter rather than computing it internally. Its decision, evaluated after the existing embedding-then-fuzzy similarity search (WR-21) completes:
- Similarity finds a category **and** the LLM independently found the **same** category → auto-assign it, `category_source = similarity` (unchanged end result from before this feature).
- Similarity finds a category but the LLM abstained (returned `UNSURE`) → the similarity result wins directly, `category_source = similarity` (not a disagreement — nothing to disagree with).
- Similarity finds nothing but the LLM found a category → the LLM result wins directly, `category_source = llm` (not a disagreement).
- Similarity finds a category **and** the LLM finds a **different** category → genuine disagreement: the transaction is persisted with `category_source = unsure` and a new `CategorizationDisagreement` row is recorded (Database `BR-26`/`BR-27`) carrying both candidate categories — no auto-assignment either way.
- Neither finds anything → `category_source = unsure`, unchanged from before this feature.

Whatever the LLM answered (a real category, or `UNSURE`) is persisted to the transaction's own `llm_suggested_category_id` (Database `BR-26`) regardless of which branch above was taken — `UNSURE` persists as `null` (BR-26), a real category persists as that category's id. This happens once, at transaction creation, and is never revisited. **Traces to**: FR-MPR-1, FR-MPR-6, FR-MPR-9.

## WR-29: Price-Range Bucket in Embedded Text (added 2026-08-16 — Matching Precision Refinement)
The text passed to `computeEmbedding()` for both a transaction's own persisted embedding and a query-time transient embedding (all call sites: `findSimilarPastTransaction`, `recategorizeUnsureFromPrecedent`'s pairwise check, `matchNewTransaction`, `runDetectionScan`'s group-merge pass, and `processNextEmbeddingBatch`) is no longer the raw description/name alone (superseding WR-24 for this feature's scope) — it is `"{description} | {price bucket label}"`, where the price bucket is derived from the transaction's amount (or the `RecurringPayment`'s `expected_amount`) against a configurable, ascending list of boundaries (e.g. `$0 to $1`, `$1 to $5`, `$5 to $10`, ... up to an open-ended top bucket, e.g. `$5000+`). Boundaries are env-configurable (a comma-separated ascending list), not hardcoded. WR-24's "raw, unmodified text" principle still holds for the description/name portion itself — WR-20's `normalize_reference_noise` is still never applied before embedding; only the price-bucket suffix is new. **Traces to**: FR-MPR-4, FR-MPR-5.

## WR-30: Embedding Score Boost on LLM-Category Agreement (added 2026-08-16 — Matching Precision Refinement)
A small, configurable boost (`embedding_llm_agreement_boost`, raw 0.0-1.0 cosine scale, added then capped at 1.0) is applied to a candidate's raw cosine score, before the `embedding_similarity_threshold` eligibility check (WR-23), when an LLM-classification-based agreement signal is present — never a penalty on disagreement, only a boost withheld. The specific agreement compared differs by call site, per Application Design Decision 4:
- `findSimilarPastTransaction`: boost when the embedding-found candidate's actual (already-assigned) category agrees with the transaction currently being categorized's own LLM classification (WR-27/28 — already in hand at this point in `categorize()`'s flow).
- `recategorizeUnsureFromPrecedent`'s pairwise check: boost when the **candidate** transaction's own persisted `llm_suggested_category_id` (WR-28, set back when that candidate was originally ingested) agrees with the category being **proposed** (the corrected source transaction's category) — the candidate's LLM opinion, read back later, either corroborates or doesn't corroborate the re-categorization being proposed for it.
- `matchNewTransaction`: boost when a candidate `RecurringPayment`'s own (optional) `category` agrees with the newly-ingested transaction's LLM classification (WR-27/28, same transaction, already known).
- `runDetectionScan`'s group-merge pass: boost when either group representative's own LLM-classification (if persisted, i.e. that representative was ingested after this feature shipped) agrees with the *other* representative's actual assigned category — checked symmetrically (either direction agreeing is enough).

**Traces to**: FR-MPR-7.

## WR-31: Raised Embedding Similarity Threshold (added 2026-08-16 — Matching Precision Refinement)
`embedding_similarity_threshold` is raised from 0.75 to 0.82 (implementation-chosen default per the requirements' Deferred-to-Code-Generation note) — a moderate increase (+0.07 on the 0.0-1.0 cosine scale) intended to reject more borderline near-matches than the original Epic 9 default allowed, consistent with the user's "increase the threshold a little" framing, while the new price-bucket text (WR-29) and LLM-agreement boost (WR-30) work alongside it as independent, complementary tightening/loosening signals rather than a single lever doing all the work — the threshold increase alone is not expected to fully address over-eager matching; it is one of three coordinated changes. Same env-tunable convention as before (`EMBEDDING_SIMILARITY_THRESHOLD`), not hardcoded. **Traces to**: FR-MPR-8.

## WR-32: Re-Embedding Existing Rows After the Price-Bucket Text Change (added 2026-08-16 — Matching Precision Refinement)
Because WR-29 changes what text every embedding is computed from, every `Transaction` and `RecurringPayment` row already at `embedding_status = completed` before this feature has a stale vector (missing the price-bucket suffix) that would otherwise never be recomputed. A one-time data migration (Database unit, retroactively added — same precedent as `RecurringPayment.embedding_status` itself being added retroactively during Epic 9's Ingestion Worker Functional Design) resets every row's `embedding_status` back to `pending` exactly once, on deploy of this feature. No new code path is needed beyond that reset: the existing `processNextEmbeddingBatch()` mechanism (WR-26) already drains the `pending` backlog identically regardless of whether a row is brand-new or being re-embedded — the same "one unified mechanism" principle WR-26 already established. **Traces to**: FR-MPR-4, NFR-MPR-3.

## WR-33: Settings Override File Takes Precedence Over Process Environment, Via a Custom Source Order (added 2026-08-16 — Configurable Application Settings)
`config.py`'s `Settings` class is extended with a `settings_customise_sources()` override (pydantic-settings' documented extension point for controlling source precedence) that injects a `DotEnvSettingsSource` pointed at the shared override-settings file (Key Design Resolution 3, Application Design) as the **highest-precedence** source — checked *before* the default process-environment source, not after.

This is a resolved technical decision, not a restatement of Requirements' Resolved Decision 3 — investigating the actual mechanism (empirically, not assumed) surfaced a real conflict pydantic-settings' *default* source ordering would otherwise have caused: pydantic-settings' out-of-the-box precedence is init args > process env > `env_file` > secrets > field defaults, meaning a plain `env_file=...` config (the literal reading of "loaded via pydantic's `env_file` support") would have made the override file **permanently ineffective** for every one of the 35 settings that `docker-compose.yml` already explicitly maps into the container's process environment (verified by actually constructing a `Settings`-equivalent test object with both sources present — the process-env value won every time, silently). `settings_customise_sources()` is pydantic-settings' own documented way to reorder or add sources; putting the override file first there gives it real, unconditional priority over whatever `docker-compose.yml`/root `.env` supplied, which is what "override" has to mean for this feature to do anything. Root `.env`/`docker-compose.yml` remain completely unchanged as the deployment-time default layer (Infrastructure Design closes the pre-existing mapping gap there separately, WR-33 does not depend on that gap being closed) — this mechanism only adds a new, higher-priority layer on top, it does not touch or need to read `.env` directly at all.

`extra = "ignore"` is also added to `model_config` (previously implicit/default-equivalent, now load-bearing): the shared override file can contain keys belonging to either service (`api-service`-owned settings alongside `ingestion-worker`-owned ones, per Application Design's single-shared-file decision), and each service's `Settings` class must silently skip keys it doesn't define as a field rather than raising `extra_forbidden` — verified this is in fact pydantic-settings' actual failure mode without it, by constructing a `Settings`-equivalent test object against a file containing an unrecognized key. **Traces to**: FR-CAS-4, FR-CAS-5.

## WR-34: Categorization Prompt Includes Converted Amount (added 2026-08-17 — Categorization Model Fine-Tuning)
`classify_description`/`classify_descriptions_batch` (the OpenRouter client functions `llm_classifier.py` calls) now build their prompt text from both `description` and `amountSgd` (the transaction's `converted_amount_sgd`), not `description` alone. Exact prompt wording/formatting is an implementation-level choice made at Code Generation, not fixed here — the requirement is only that both values reach the model, not a specific string layout. Bank name is deliberately excluded (Requirements' Resolved Decision 5 — "a very weak signal," user's own words). This exists purely to keep the live inference input shape identical to what the Model Training unit's Dataset Curator (Unit 5) trains against (Requirements' Resolved Decision 6) — without it, a fine-tuned model would be evaluated/used against a different input shape than it was trained on. **Traces to**: FR-CFT-9.

**Correction found at Code Generation**: this rule's first draft assumed `converted_amount_sgd` was already available at the Ingestion Orchestrator's existing per-file `classifyBatch` call site. Actually reading `orchestrator/pipeline.py` showed currency conversion ran *later* than that — per-transaction, inside `_persist_transaction`, after the upfront batch classify call — so the amount genuinely didn't exist yet at that point. Fixed by moving conversion resolution earlier: it's now computed upfront per transaction (same `resolve_converted_amount` call, same FX-cache reads/writes, no behavior change to conversion itself), passed into `classifyBatch` for the prompt, then reused (not recomputed) at persist time. See `business-logic-model.md`'s corresponding note.

## WR-35: Recategorization Re-Scan Uses a Broadened, Category-Filtered Precedent Pool (added 2026-08-28 — Recategorization Algorithm Rework)
`recategorizeUnsureFromPrecedent` (WR-5) no longer compares each `UNSURE` candidate against only the single just-corrected source transaction (a one-off pairwise cosine check). It now searches the `transactions` vector-store collection for the candidate's top-`embedding_top_k` nearest neighbors (the same `queryNearestNeighbors` call `findSimilarPastTransaction` already uses, WR-21), fetches their full rows, and filters to only those whose current category equals the category the source transaction was just corrected to — the best-scoring match among that filtered set (if any) is the candidate's match. Unlike `findSimilarPastTransaction`, this is deliberately **not** an unconstrained "closest match in all of history" search: a candidate's true nearest neighbor overall might belong to some other category entirely, in which case this re-scan run finds no match for it (it isn't this specific correction's concern) rather than proposing the wrong category just because *something* was close.

The fuzzy-text fallback (used when embedding computation/query is unavailable, WR-21 step 4) gets equivalent treatment: its candidate list is now `listSimilarityCandidates()` filtered to the corrected category, replacing the single `source_candidate` it used to check against.

**Feasibility note**: Qdrant points in this project's vector store carry no payload metadata (id + vector only) — there is no native category filter at the query layer. Category filtering happens in application code, after fetching the top-K candidates' rows, not via a Qdrant-side filter. Extending the schema to support native filtering was considered and explicitly deferred (out of scope — the embedding-accuracy focus of this rework does not require it; see the requirements document's FR-RAR-1 discussion). **Traces to**: FR-RAR-1.

## WR-36: Direction Signal Added to Embedded Text (added 2026-08-28 — Recategorization Algorithm Rework)
`build_embedding_text` (Embedding Manager) now appends a direction token — `"inflow"` or `"outflow"`, derived from whether the transaction's `in_flow` or `out_flow` field is set (BR-2: exactly one always is) — alongside the existing price-range bucket (WR-29): `"{description} | {price bucket} | {direction}"`. This applies to the function itself, so it takes effect at all of its call sites without exception: `findSimilarPastTransaction` and `recategorizeUnsureFromPrecedent` (Categorization Engine), `matchNewTransaction` (Recurring Payment Manager), and `processNextEmbeddingBatch` (Embedding Manager's storage-time batch job) — one shared fix, not a re-scan-specific fork of the function, per the user's explicit direction during Requirements Analysis. **Traces to**: FR-RAR-6.

## WR-37: Delimiter-Based Reference-Code Stripping Before Embedding (added 2026-08-28 — Recategorization Algorithm Rework)
Before `build_embedding_text` embeds a description, text following specific known boilerplate delimiters is stripped: `"OTHR-"`, `"OTHR - "`, and `"REF:"` (case-insensitive; whichever occurs first in the string, if any) — everything from the delimiter onward is dropped. This targets the exact noise pattern found in the evidence gathered during Requirements Analysis (e.g. `"...OTHR-DICNP17537901512105MMHTZ8"`, `"...OTHR - EPOSSPSPTWM8J GOJ IIFTRGNB"`), a deliberately conservative, delimiter-anchored heuristic rather than a blanket "strip any long alphanumeric token" rule (the user's explicit choice during Functional Design, over a broader heuristic that was also proposed) — chosen specifically to avoid any risk of stripping genuine merchant/payee name text that happens to contain digits.

This stripping applies only to the text passed into `computeEmbedding()` — the stored `Transaction.description` field itself is completely unchanged (still the full raw statement text, used as-is everywhere else: UI display, LLM classification input via `classifyBatch`/`classify` WR-27, etc.). Like WR-36, this is a change to the shared `build_embedding_text` function, so it applies at all of its call sites, not just the re-scan. **Traces to**: FR-RAR-7.

## WR-38: Embedding Threshold Reconciled to Code Default (added 2026-08-28 — Recategorization Algorithm Rework)
The live `EMBEDDING_SIMILARITY_THRESHOLD` override (`.env` = 0.75) is reconciled to `config.py`'s coded default (0.82, set by WR-31) — the override is removed rather than the code changed, since no documented reason for the divergence was found and 0.82 was itself a deliberate, evidence-considered choice (WR-31). No other threshold values (`similarity_threshold`, `recategorization_auto_apply_threshold`) change in this pass — the user's explicit choice was to let the retrieval-strategy change (WR-35) and embedding-text changes (WR-36/37) do the precision work first, and re-tune specific numbers later based on real results rather than guessing new values now. **Traces to**: FR-RAR-3, FR-RAR-5.

## WR-39: Full Re-Embedding Backfill, Vectors Only — Categories Untouched (added 2026-08-28, revised 2026-08-28 — Recategorization Algorithm Rework)
**Supersedes this rule's first draft** (which had opted to accept a temporary mismatch instead — reversed after the user clarified, following WR-32's precedent, that a full backfill should happen). Every already-embedded `Transaction` and `RecurringPayment` row is reset to `embedding_status = 'pending'` via a one-time migration, exactly matching WR-32's mechanism when `build_embedding_text`'s format last changed (WR-29) — the existing `processNextEmbeddingBatch` job (WR-26) then re-embeds the full backlog under the new WR-36/37 text format with no new code path needed, the same "one unified mechanism" precedent WR-26/WR-32 already established.

**Hard constraint (explicit user requirement)**: this backfill MUST touch embeddings only — `category_id`, `category_source`, and every other transaction field besides `embedding_status`/the vector itself MUST remain completely unchanged. `processNextEmbeddingBatch` already satisfies this by construction (it calls `computeEmbedding` + `upsertEmbedding` + flips `embedding_status` — no categorization logic runs in that job, `categorize()`/`recategorize_unsure_from_precedent` are never invoked from it), so no new guard is needed to prevent it; this is called out explicitly here anyway, as a requirement Code Generation and Build and Test must both verify (e.g. a live before/after category-snapshot comparison), not merely infer from reading today's code. **Traces to**: NFR-RAR-3.

## WR-40: Generic Boilerplate Phrase Stripping + Concurrent Backfill (added 2026-08-29 — Recategorization Algorithm Rework, live-trial follow-up)
Found via interactive live trials (user-driven: giving a real description, inspecting the closest matches `find_similar_transaction_via_embedding` would actually return): a second boilerplate-domination pattern distinct from WR-37's PayNow `OTHR-`/`REF:` case. Real example: `"MISTER MINIT ARC Card Payment"` (Electronics) and `"AMAZON MKTPLC Card Payment"` (Online Shopping) — two unrelated merchants — scored *higher* against each other (88-89% cosine) than the genuine `"M1 LIMITED M1APP+ SINGAPORE SG"` precedent scored against a same-merchant query (87.91%), purely from sharing the generic `"... Card Payment"` card-transaction suffix.

`build_embedding_text` (`embedding/text.py`) now also strips the literal phrase `"Card Payment"` (case-insensitive, word-boundary-anchored) wherever it occurs, not just as a suffix — added as a second, independent stripping pass alongside WR-37's delimiter-anchored one (`_BOILERPLATE_PHRASE_PATTERN`, distinct from `_REFERENCE_NOISE_PATTERN` since this phrase *is* the noise, not a marker for what follows it). Applied via the same shared function, so it reaches all consumers exactly like WR-36/37 already do.

**Backfill re-triggered** (same WR-39 mechanism — every already-`completed` row reset to `pending`) since this changes what every embedding is computed from, again. **Speed-up added per explicit user request** ("use more cores"): `processNextEmbeddingBatch` (`embedding/service.py`) now computes each batch's embeddings concurrently via a bounded `ThreadPoolExecutor` (`embedding_concurrency`, default 5 — same value and same overload reasoning as `llm_classification_concurrency`, same local model server), rather than one HTTP round-trip at a time. Order-preserving: each row's vector is still written against that same row (never mixed up across concurrent completions), and the "stop early on first failure" behavior (WR-25/FR-10) is preserved for the DB-write phase, applied in the batch's original deterministic order even though the underlying HTTP calls that produced the vectors ran concurrently. **Traces to**: user-reported live-trial finding, no formal FR (post-Build-and-Test refinement, not a new Requirements Analysis round — narrow, well-understood extension of the already-approved WR-37/39 mechanisms).

## WR-41: PayNow-Mobile Transfers Exempted From Reference-Noise Stripping (added 2026-08-29 — Recategorization Algorithm Rework, live-trial follow-up)
Found via the same live-trial process as WR-40, specifically the `"FAST PAYMENT via PayNow-Mobile to Verena OTHR-..."` family of examples: WR-37's stripping was removing genuine signal, not noise, for this transfer type. Real evidence: `OTHR-shanghai trip` (Vacation), `OTHR-gold bar` (Others), `OTHR-hongbaos` (Gift) — all transfers to the same person, `Verena`, distinguished ONLY by the free-text note after `OTHR-`, which the user relied on to categorize each one differently. Stripping that note (as WR-37 does for merchant/business PayNow-UEN payments, where the equivalent text is a random reference code) collapses these into indistinguishable queries.

`_strip_reference_noise` (`embedding/text.py`) now checks for the literal marker `"PayNow-Mobile"` (case-insensitive) before applying WR-37's `OTHR-`/`REF:` stripping — if present, the stripping step is skipped entirely for that description (WR-40's `"Card Payment"` phrase stripping still applies regardless, since that's unrelated boilerplate). This is a principled distinction, not a heuristic guess: `PayNow-Mobile` (pay by phone number) is Singapore's person-to-person PayNow rail, while `PayNow-UEN` (pay by Unique Entity Number, a business registration identifier) is specifically for registered businesses — the rail name itself reliably signals which kind of free text follows. **Traces to**: user-reported live-trial finding, same no-formal-FR reasoning as WR-40.

## WR-42: Embedding Similarity Threshold Raised to 0.92, Auto-Apply Threshold Re-Confirmed at 97 (added 2026-08-29 — Recategorization Algorithm Rework, live-trial follow-up)
A systematic live-trial evaluation (20 randomly-sampled real, confidently-categorized transactions, each checked against its own top-8 nearest neighbors in the real vector store — 160 same-category/different-category data points total) measured actual precision at different score thresholds against this deployment's real data:

| Score band | Precision |
|---|---|
| ≥ 97 | 100% (n=6) |
| ≥ 92 | 67% (n=86) |
| ≥ 85 (old pending-review floor) | 62% (n=134) |
| ≥ 82 (previous `embedding_similarity_threshold`, WR-38) | 62% (n=134) |

Two findings, two decisions:
- `embedding_similarity_threshold` (the pending-proposal eligibility floor) raised from `0.82` to `0.92` (`config.py`'s coded default and `.env`'s explicit override, kept in sync per WR-38's precedent) — 0.82 was letting through matches with only ~62% real-world precision; 0.92 measurably improves that to ~67% on a comparably-sized sample. Still imperfect (this embedding space doesn't cleanly separate "worth reviewing" from "wrong" in the 82-96 band), but a clear, evidence-backed improvement over the prior value.
- `recategorization_auto_apply_threshold` (97.0, unchanged since WR-9) is explicitly **re-confirmed, not changed** — the same evaluation found 100% precision at/above it (small sample, n=6, but consistent with a real cliff observed immediately below it: 96 scored 0/2, 95 scored 3/8) and with the pattern seen repeatedly across individual live trials (e.g. a genuine same-merchant match scoring ~98 with the nearest wrong-merchant match ~20 points below it).

**Traces to**: user-reported live-trial finding, same no-formal-FR reasoning as WR-40/41 — this is threshold recalibration within the already-approved FR-RAR-3/FR-RAR-5 scope (precision-first tuning, threshold reconciliation), not new scope.

## WR-43: Already-Categorized Bucket Reintroduced as a Never-Auto-Apply Review Flag (added 2026-08-29 — Recategorization Algorithm Rework, live-trial follow-up)
**Explicit user request, deliberately reversing WR-9's revision (2026-08-19, Recategorization Scope Narrowing)**, which removed the "already-categorized" bucket entirely because its matches were observed to be low-accuracy and risked silently suggesting the wrong overwrite for an already-correctly-categorized transaction. Two things changed since then that motivated bringing it back: (1) everything else in this rework session (WR-35 broadened pool, WR-37/40/41 noise stripping, WR-42 recalibrated threshold) substantially improved match quality, and (2) this reintroduction carries an absolute safety rule the original bucket's removal reasoning was specifically worried about — it can **never auto-apply, regardless of score** (WR-10's original rule, still enforced exactly as before; only ever creates a `PENDING` `RecategorizationProposal`, `source_bucket = 'categorized'` — the same enum value the original bucket used, unchanged in the schema since WR-9's revision explicitly kept it for historical rows).

`recategorize_unsure_from_precedent` now does a second pass after its existing UNSURE-bucket loop: a single embedding search for `source_transaction` itself (source-centric, not candidate-centric like the UNSURE loop — one search finds every qualifying candidate at once, rather than checking every already-categorized transaction in the database individually, which would be prohibitively expensive against a database of thousands). Each of the source's top-`embedding_top_k` nearest neighbors is flagged (as a `PENDING` `CATEGORIZED`-bucket proposal) if: its `category_source` is not `UNSURE` (that's the first bucket's territory), its category differs from the one just corrected to, its score clears `embedding_similarity_threshold`, and it isn't already sitting on an unresolved `PENDING` proposal from an earlier job (same Issue #12 dedup reasoning as `find_unsure_transactions`, factored into a new shared repository query, `list_pending_proposal_candidate_ids`). Same WR-21-style whole-operation fuzzy-text fallback as the rest of this function: if the embedding path is unavailable or finds nothing, a single best fuzzy-text match among every confidently-categorized, different-category candidate is flagged instead.

**Traces to**: explicit user request ("if I were to manually change the category of a transaction, the recategorisation scanning should flash up existing highly similar transactions that is not the same category, for review") — a deliberate, explicit reopening of WR-9's prior scope decision, not new/undiscussed scope; same no-formal-FR reasoning as WR-40/41/42 for this live-trial-driven session.
