# NFR Design Patterns — Model Training Unit

## Fail-Loud, Not Fail-Silent
Every external dependency call (DB query, HuggingFace download, ClearML init, oMLX HTTP call) is allowed to raise and terminate the script with a non-zero exit code and a clear message — deliberately **not** wrapped in `ingestion-worker`'s "never raises, degrade to UNSURE" pattern (WR-4). That pattern exists because ingestion is an unattended background process where one bad transaction shouldn't abort a whole run; this is a manually-run, single-operator tool where a silent partial failure (half a dataset, a training run that silently skipped evaluation) is far worse than a stack trace the operator can read and re-run after fixing.

## Read-Only Session Discipline
The Dataset Curator opens its DB session the same way `ingestion-worker`/`api-service` do (`transactagent_db`'s existing `SessionLocal`/engine setup, reused directly) but never calls `.add()`/`.commit()`/`.flush()` with pending writes — enforced by code review discipline and a dedicated test (NFR-CFT-2/6) asserting the query functions only ever execute `SELECT` statements, not by a separate DB permission layer (see NFR Requirements' Security section for why a new role was rejected).

## Config Loading — Reuses, Does Not Duplicate
`model_training/config.py` is a `pydantic-settings` `Settings` class reading the **same** `DB_HOST`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`/`OPENROUTER_BASE_URL`/`OPENROUTER_MODEL`/`OPENROUTER_API_KEY` env vars the other units already define in `.env` — not a copy of their values, not a separate settings-override mechanism (AR-32/WR-33's override-file precedence is a `docker-compose`-only concept for the 2 containerized services; Model Training runs on the host and reads `.env` directly via `pydantic-settings`' own `env_file` support, the simplest mechanism that fits a host-run script — no separate `python-dotenv` call needed, even though it's a transitive dependency either way). ClearML credentials are deliberately **not** read through this `Settings` class at all — they flow through ClearML's own standard mechanism (`clearml.conf`/`CLEARML_API_*` env vars), so this project's config layer never needs to know ClearML credentials exist.

## Two-Speed Testability
Per NFR Requirements: pure logic (SQL-shape assembly, JSONL serialization, accuracy/confusion-matrix computation, prompt-template rendering) lives in small functions with no ML-runtime dependency, each independently `pytest`-covered. Anything touching `mlx_tune`/`clearml`/a real HTTP call to oMLX is deliberately kept in thin wrapper functions at the top of `train.py`'s call graph — not because they're untested, but because their real verification is a live smoke run (Build and Test), not a mock standing in for genuine ML behavior.
