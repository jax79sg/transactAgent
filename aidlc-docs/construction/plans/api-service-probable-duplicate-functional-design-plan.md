# Functional Design Plan — API Service Unit: Probable Duplicate Statement Detection (Epic 14)

Unit: API Service (Unit 2). Scope: the new Duplicate Review Component (pairs, comparisons, the removal request, dismissal, override, re-check), one extended field set on the run-file detail, and three new settings on the existing Settings catalog. Technology-agnostic: logical endpoints, shapes and rules; module layout, SQL and test code are Code Generation.

**No open questions.** Every product decision was settled by the approved requirements, the stories and their dated amendments (including Question 1 = C), the Database design, and the Ingestion Worker design. What remains at this level is the API's shape, and each choice below follows from those or from this service's existing conventions (a router per component, a service module, camelCase DTOs, typed errors, session-per-request, router-level authentication). The table gives the reasoning so you can overrule any row at approval.

## Design decisions made and explained (not asked), with reasoning

| Topic | Decision | Why this isn't a question |
|---|---|---|
| **A new router, `/duplicates`, behind the existing authentication** | One router for the Duplicate Review Component, with the same router-level login requirement as every other router. Endpoints: list pairs; pending count; one comparison; confirm a removal; dismiss a pair; override a skipped file; scan status; request a re-check. | Application Design (a component per concern) and NFR-PD-8 (same authentication). |
| **DB-only, and a short list of writes** | It reads pairs, comparisons, remembered files, removal jobs, scan state, statements, transactions and their dependents. It writes only: a removal job (confirm), a pair's status (dismiss), a remembered file's state (override), and the scan state's re-check time. It never calls the worker and never touches the vector store. | NFR-PD-4 and the project's one hard rule. |
| **What the Review panel lists** | Three groups, newest first within each: (1) **pending pairs** (including information-only ones, which is what the Question 1 = C story amendment says counts in the badge until dismissed); (2) pairs whose **removal is in flight** (job queued, running, or embeddings pending); (3) pairs **removed in the last 24 hours**, so the outcome (done, and the counts deleted, or "embeddings cleanup failed, harmless") stays visible after the pair has left `pending`. After 24 hours a removed pair drops out of the panel; the permanent record stays in the database. Paginated like the other review lists. | The Database design moves a pair to `removed` the moment the deletion commits (WR-67), so a list of only pending pairs would make a removal vanish before the user sees it finish (US-14.6's "pending, then done or failed"). A fixed window follows the Background Activity precedent (AR-36). |
| **The badge count** | Pending pairs with **no active removal job**. | A pair with a removal in flight has had its decision made; the Database lifecycle states this. Information-only pairs count (Question 1 = C). |
| **Labels and counts** | Each side's label (file name, bank, period, transaction count) is read from the **stored comparison**, so it survives later changes. The manual-correction counts and the removal preview are read **live** from the statements (found by content hash). A pair whose statement is gone is marked stale: no counts, no removal offered. | The comparison is write-once evidence; corrections change as the user works (Database design). |
| **The removal preview** | `{transactions, statementSections, recategorizationJobs, recategorizationProposals, categorizationDisagreements, recurringPaymentMatches, correctionsLost, onlyOnRemovedCopy}`. The first six are live counts over the same dependents list the worker deletes (BR-51; the Database unit's guard test fails if that list ever changes without these three places being updated). `onlyOnRemovedCopy` is the removed side's stored transaction count minus the stored matched count, so the API needs no copy of the matching rule. Computed only for a pending pair where removal is offered. | FR-PD-12 and the Question 1 = C story amendment (the confirmation states how many transactions exist only on the copy being removed). Matching is one-to-one, so "count minus matched" is exactly the number with no match. |
| **Confirming a removal: ordered checks, then one insert** | In this order, each a typed error: the pair exists (404); is `pending` (409); has `removal_allowed` (409, "removal not offered"); has no active job (409); both statements still exist (409); the hash the user confirmed is the pair's **non-keep** hash (409, "out of date"); and the live manual-correction count on that copy **equals** what the user was shown (409, "out of date"). Then insert one `queued` job carrying that count. A race with a second confirmation is caught by the active-job unique index and reported as the same "already requested". | NFR-PD-3. The API requires an exact match because the user acknowledged an exact number; the worker re-verifies later with "not more than" (WR-66), so a correction added in the gap is still caught. Nothing is deleted by the API. |
| **Dismissing** | Allowed for a `pending` pair with no active job (information-only pairs included): set `dismissed` and `decided_at`. Final; there is no "undo dismiss". The update is a single conditional write so a concurrent scan refresh cannot overwrite it. | FR-PD-10, A-PD-5, BR-44 (dismissed is final). |
| **Overriding a skipped file** | Finds the remembered file for the comparison (`probable_duplicate` or `confirmed_duplicate`) and sets `overridden` and `decided_at`. Idempotent: an already overridden file returns its state unchanged. Takes effect on the next ingestion run (A-PD-4). Also allowed for a **removed** copy (the Database design's BR-41 decision, confirmed at its approval); the response notes that corrections lost with it are not restored. A comparison with no skipped file (a held pair) is a 409. | FR-PD-7, BR-41. |
| **The comparison view's state** | One derived field: `skipped`, `ingest_at_next_run`, `ingested_at_your_request`, `removed`, `pair_pending`, `pair_dismissed`, or `pair_superseded`. For a skipped file it also says **which side is "this file"** (the side whose hash is the remembered file's), so the view can show "this file" against "the statement it matches". It carries the stored reason (which already states a size difference prominently, WR-60), and for a held pair whether removal is offered. | US-14.2, US-14.3 ("after ingestion it shows it was ingested at my request"), Question 1 = C. |
| **Scan status and re-check** | Status: when the last scan completed, how many pairs it found, whether a re-check is waiting, and whether detection is **switched on** in the effective settings (so an empty panel can say "detection is off" rather than "no duplicates"). A re-check request sets the scan state's re-check time (creating the single row if it does not exist). | The worker owns the scan; the API only records the request (BR-48, WR-63). |
| **Run-file detail** | The run-file detail gains `duplicateComparisonId` and a structured `matchedStatement` (the label of the statement the file was judged a duplicate of), and its `outcome` may be `skipped_probable_duplicate`. The matched side is the comparison side whose hash equals the remembered file's matched hash. The Frontend formats "probable duplicate of <file name> (bank, period)". | US-14.1/14.2, A-PD-3. A structured label keeps formatting in one place (the Frontend). |
| **Settings: three catalog entries, a new category** | Category "Duplicate Statements". `duplicate_detection_enabled`: standard, an enumerated choice of `false`/`true`, default `false`, description saying it should be switched on only after the `check-duplicates` accuracy check and takes effect when the worker restarts. `duplicate_match_ratio`: standard, decimal 0.50 to 1.00, default 0.80. `duplicate_min_transactions`: advanced, whole number 1 to 50, default 3. The catalog grows from 44 to **47** entries and the two tests that assert the count change with it. | AR-28's allow-list is the only way a setting exists. The catalog has no boolean type (only decimal, whole number, text, and enumerated), and adding one is a larger change than a two-value enumerated choice, which the Settings page can show as a dropdown (it does not today: every setting is edited in a text box, so the Frontend design adds a dropdown for enumerated settings; this was wrongly stated here as already existing and was corrected at Frontend Functional Design, 2026-10-04). |
| **A small fix the boolean exposes** | The Settings service renders a non-overridden value with plain string conversion, which turns a true/false value into "True"/"False" and would not match the choice's allowed values. It lowercases booleans. The API's display-only mirror of the worker's settings gains the three fields. | Found by reading the code, not by running it: without this the switch would display as an unrecognised value on every fresh deployment. |
| **Errors** | New typed errors with stable codes: `pair_not_pending`, `removal_not_offered`, `removal_already_requested`, `statement_missing`, `confirmation_out_of_date`, `not_a_skipped_file`; plus the existing not-found. All use the existing consistent error shape. | The Frontend has one error-handling path (the Error Shape section). |
| **Atomicity** | Each action is one request, one transaction (the existing session-per-request commit). The conditional writes (dismiss, override, job insert) make a lost race an explicit error, never a silent overwrite. | AR-33's reasoning for settings, applied here. |
| **No new table and no worker call** | Nothing new in the schema beyond the Database unit (and its one reopened column, `removal_allowed`, which the API reads and never writes). | Scope. |
