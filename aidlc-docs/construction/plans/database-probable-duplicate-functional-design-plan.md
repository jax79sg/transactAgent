# Functional Design Plan — Database Unit: Probable Duplicate Statement Detection (Epic 14)

Unit: Database. Scope: six new entities, one new run-file outcome with one new link on `IngestionRunFile`, and the invariants that keep them consistent. Technology-agnostic: logical types only; exact column types, indexes, and the migration (0020) are Code Generation.

**No open questions.** Two rounds of requirements questions and eight documented assumptions settled the product decisions, and Application Design settled the component split. What remains at this level is data shape, and each choice below follows from an approved requirement or from this project's existing data-model conventions. The table gives the reasoning so you can overrule any row at approval.

## Design decisions made and explained (not asked), with reasoning

| Topic | Decision | Why this isn't a question |
|---|---|---|
| **Everything new refers to statements by content hash, with no foreign key to `bank_statements`, `statement_accounts`, or `transactions`** | `KnownFile`, `DuplicatePair`, and the comparison's sides hold a statement's `pdf_content_hash`; nothing new points at a statement row. | Approved at Application Design ("keyed by content hash"). It has a consequence worth stating: the Account Balance backfill's wipe order (BR-36) and the removal helper's delete order do not change, because nothing new depends on a statement or transaction row. A row-id link would block every wipe and every removal. |
| **`KnownFile`: one row per content hash** | `pdf_content_hash` (unique), `state` (`probable_duplicate` \| `overridden` \| `confirmed_duplicate`), `matched_statement_hash`, `comparison_id` (FK, required), `created_at`, `updated_at`, `decided_at` (set when overridden). All three states always carry their evidence, so the matched hash and comparison are required. | FR-PD-8/13/7 and A-PD-8. Requiring the evidence means a run result can always link to a comparison (US-14.2/14.4) and the backfill can always carry corrections to the kept copy (FR-PD-17). |
| **State changes on `KnownFile`** | A row is inserted as `probable_duplicate` (skipped at ingestion, or pre-registered by the backfill) or as `confirmed_duplicate` (a removal completed). The only change after insertion is to `overridden`, from either of the other two states. `overridden` is final. | **Goes slightly beyond the stories, flagged for you.** US-14.3 covers overriding a skipped file; it does not say whether a *removed* copy can be overridden. Removal is a permanent delete (Q5 = A) and the Drive file is left alone, so without this the only way to bring a wrongly removed copy back would be restoring a backup, with no in-app path. Allowing it reuses the same "Not a duplicate — ingest it" action from the run-results link; the corrections that sat on the removed copy are still not restored, and the comparison view will say so. One line to reverse if you disagree. |
| **Comparison snapshot is stored once and shared** | `DuplicateComparison`: `id`, a record for each of two sides, `matched_count`, `match_ratio`, `reason` (text), `created_at`. The sides are named **earlier** and **later** (the earlier-ingested statement, which is the original, and the later one, which is the skipped file or the later copy of a pair). Each side holds `content_hash`, `file_name` (nullable), `bank_name`, `period_start`, `period_end`, `transaction_count`. Write-once. | FR-PD-5/6. Neutral side names work for both a skipped file (original vs skipped file) and a pair of held statements. The file name is nullable because `bank_statements` has no file name: it is resolved from the run file that processed the statement when the comparison is made and stored here, so it survives later changes (Application Design carry-forward 3). Where it cannot be resolved, the view falls back to bank and period. |
| **Snapshot rows are a child table, not a JSON column** | `DuplicateComparisonRow`: `comparison_id` (FK, cascade), `side` (`earlier` \| `later`), `rank` (1 to 10, unique per comparison and side; rank 1 is the largest amount, ties earlier date first), `transaction_date`, `description`, the amount as `out_flow` or `in_flow` (exactly one, the same convention as `Transaction`), `currency`, `marker` (`also_on_other` \| `only_on_this_one`). | The project stores no JSON anywhere, and a child table lets the database itself enforce "at most 10 per side" (FR-PD-5) with a rank bound and a uniqueness rule instead of trusting the application. Amounts are in the statement's own currency, as printed, because that is what a person comparing two statements expects to see. |
| **A pair of already-held statements** | `DuplicatePair`: `id`, `hash_a` and `hash_b` (canonical order: `hash_a` is the smaller, so the pair is unordered and unique), `comparison_id` (FK, required), `keep_hash` (one of the two: the worker's proposal, FR-PD-11), `status` (`pending` \| `dismissed` \| `removed` \| `superseded`), `found_at`, `decided_at`. | FR-PD-9/10 and A-PD-5/6. `keep_hash` is stored because the proposal is computed once by the worker and only displayed by the API (Application Design rule), so the two services can never disagree about which copy goes. Manual-correction counts are **not** stored: they change as the user works, and the panel reads them live. |
| **`superseded`, not delete** | When the backfill's reingest resolves a pending pair, or a scan finds a pending pair whose statements are no longer both held, the pair is marked `superseded` instead of being deleted. | Keeps the history and avoids a foreign-key knot: a failed removal job may still reference the pair (next row), and deleting the pair would force deleting the job's record too. `dismissed` and `removed` are likewise kept; they are the memory that stops a pair being offered again (A-PD-5). |
| **Removal job** | `StatementRemovalJob`: `id`, `pair_id` (FK), `remove_statement_hash`, `corrections_acknowledged` (the count of manual corrections the user was told would be lost), `status` (`queued` \| `running` \| `embeddings_pending` \| `embeddings_failed` \| `completed` \| `failed`), `failure_reason`, `removed_transaction_ids` (list of ids, with no foreign key because the rows are gone), `deleted_counts` (per kind), `embedding_attempts`, `requested_at`, `started_at`, `finished_at`. At most one **active** job (`queued`, `running`, `embeddings_pending`) per pair. Jobs are kept after they finish. | FR-PD-12/14, NFR-PD-3/4. The statuses mirror `RecategorizationJob` (`queued`, `running`, `completed`, `failed`) plus the two embedding states the removal order requires: the database rows are deleted and committed first, then the embeddings. `removed_transaction_ids` is what makes a retry possible after the commit, since the transactions no longer exist to look up. `embeddings_failed` is where a job is parked after bounded retries (Application Design carry-forward 4), so it cannot block the poll loop. Keeping finished jobs is a permanent record of a permanent deletion, the same append-only reasoning as `SettingChange`. |
| **Scan state is one row** | `DuplicateScanState`: a fixed single row holding `last_scan_started_at`, `last_scan_completed_at`, `last_scan_match_ratio`, `last_scan_min_transactions`, `last_scan_pairs_found`, `recheck_requested_at`. | Backs `isPairScanDueNow` and the panel's "last checked" line. The recorded ratio and minimum are how the worker notices a settings change; which conditions make a scan due is Ingestion Worker Functional Design (Application Design carry-forward 7). A single row follows the project's single-record precedent (`OAuthCredential` per provider, `DetectionScanRun` for its due-check), enforced so a second row cannot exist. |
| **Run-file outcome and link** | `IngestionRunFile.outcome` gains `skipped_probable_duplicate`, and the entity gains a nullable `duplicate_comparison_id` (FK). Present **exactly when** the outcome is `skipped_probable_duplicate`, and such a row has no `bank_statement_id`. BR-12 (an exact-duplicate skip links to its existing statement) is unchanged. | FR-PD-2 and NFR-PD-6. A skipped probable duplicate creates no statement, so there is nothing for `bank_statement_id` to point at; the comparison is its evidence. The matched statement's label is read from the comparison, so no second link is needed. |
| **Run counters** | A file skipped as a probable duplicate counts in `files_skipped_count`, like an exact-duplicate skip, and does not make a run `completed_with_failures`. | A skip is not a failure (Application Design). Without this, every run that meets a remembered duplicate would report a failure. |
| **Backfill treatment of the new tables** | **Never wiped and never detached.** Included in the backfill's backup and restore set. The backfill adds `KnownFile` rows (pre-registration and inline skips) and marks resolved pending pairs `superseded`. | Extends BR-36. They are not wiped because they hold decisions the user made, keyed by hash so they remain valid when the statements are recreated. They are in the backup set because the backfill modifies them, and `restore` must be able to put them back. |
| **One list of what depends on a transaction** | A guard test in this unit reads the table metadata and fails if any table other than the listed ones gains a foreign-key path to `transactions`, `statement_accounts`, or `bank_statements`. | Application Design carry-forward 5. The removal helper, the backfill wipe, and the API's removal preview must agree on this list; a test over the schema is the one check that notices when a future feature adds a dependent table and forgets to add it to all three. |
| **No migration of existing data** | The migration creates empty tables and the new enum value; no existing row changes. | Nothing to backfill: existing statements are examined by the scan, not by the migration. Ships with detection off. |
