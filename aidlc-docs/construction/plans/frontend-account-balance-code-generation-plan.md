# Code Generation Plan — Frontend SPA Unit — Account Balance at a Point in Time (Epic 13)

**This plan is the single source of truth for Frontend Code Generation of this feature.** Part 1 (this document) is for approval; no code is written until it is approved.

**Unit**: Frontend SPA (Unit 4). **Stories**: US-13.2, US-13.3, US-13.4, US-13.5, US-13.6 (the screens). US-13.1 and US-13.7 were delivered by the Database and Ingestion Worker units; the API side of US-13.2 to US-13.6 by the API Service unit (approved 2026-10-18).
**Design source (approved 2026-10-18)**: the Epic 13 sections of `aidlc-docs/construction/frontend/functional-design/frontend-components.md` and `business-logic-model.md`; `construction/plans/frontend-account-balance-functional-design-plan.md` (answers, traceability, "Carried to Code Generation"); the API contract in `construction/api-service/functional-design/domain-entities.md` **as corrected on 2026-10-18** (`start`/`end`, nullable statement ids).
**Dependencies**: API Service (built, approved, **not yet deployed**: the running API container does not have the seven endpoints, `PATCH` in CORS, or the two settings until it is rebuilt and restarted at deployment). Database and Ingestion Worker: no dependency. No new npm dependency is needed (React Query, Radix Dialog and Tabs, Chart.js, react-chartjs-2, fast-check, Testing Library are all present).
**Entities owned by this unit**: none. It renders the API's DTOs and stores nothing.
**Code location**: workspace root, `frontend/` (brownfield: existing files are modified in place; new files follow the existing layout: `src/api/`, `src/lib/`, `src/components/`, `tests/`). Documentation: `aidlc-docs/construction/frontend/code/` (markdown only). Small additions outside `frontend/`: a contract drift-guard test in `api-service/tests/` (Step 3), and the e2e seed in `database/src/transactagent_db/seed_e2e_fixtures.py` with a test for it (Step 14). Nothing is written under `aidlc-docs/` except documentation.

## Approach

Bottom-up, each layer tested before the next is built on it: the contract and the types, then the pure helpers (money, balances, chart), then the components from the leaves to the tab, then the page wiring, then verification (static checks, the whole suite, a mutation check, and a look at it in a browser against a scratch API).

- **`frontend/src/api/`**: `types.ts` (+ the Epic 13 DTOs), `client.ts` (+ `PATCH`), new `accounts.ts` and `balances.ts`.
- **`frontend/src/lib/`**: new `money.ts` (exact string arithmetic and formatting), `balances.ts` (wording, dates, merge outcome, error messages), `balanceChart.ts` (ranking, folding, labels, summary); `duplicates.ts` (export `formatDay`).
- **`frontend/src/components/balances/`** (a folder, since this feature has eleven related components where Epic 14 had one): `BalancesTab`, `BalanceLookup`, `BalancesTable`, `IngestedThrough` and `UnlinkedNotice`, `BalanceChart`, `DiscrepancyPanel`, `AccountsSection`, a shared `DialogFrame`, and the four dialogs `BalanceDialog`, `RenameDialog`, `ChangeTypeDialog`, `MergeDialog`.
- **Wiring**: `DashboardPage.tsx` (fifth tab; controlled tabs; From/To box hidden on Balances; the tab strip scrolls sideways) and `SettingsPage.tsx` (`CATEGORY_ORDER` gains "Balances"). `NavBar` is unchanged (Question 5 = A).

Every interactive element and every state carries a stable `data-testid` exactly as named in the design; every element carries its `dark:` variant.

## Decisions found while planning (for review at approval)

1. **Node exists only in a container on this machine, and a bind-mounted `npm ci` or `node_modules` removal can wedge the Docker VM** (recorded after two OrbStack hangs). So the plan never installs anything over a bind mount: it keeps a **copy of `frontend/`** (with its existing linux-arm64 `node_modules`) in the session scratchpad, syncs the changed source and test files into it with `rsync`, and runs `vitest`, `tsc -b`, `eslint` and `vite build` there with `docker run --rm node:20-alpine`, each wrapped in a time limit. No dependency changes, so no install is ever needed.
2. **A two-sided contract guard, to prevent a repeat of the `start`/`end` mistake.** Step 3 adds one API test that builds a fixed scenario, calls each Epic 13 endpoint, normalises ids and timestamps, and **compares the responses with committed JSON files** in `frontend/tests/fixtures/balances/` (`UPDATE_CONTRACT_FIXTURES=1` rewrites them). The Frontend then (a) type-checks key sets against its DTO types and (b) uses these real responses as the base of its component tests. If the API's shapes change, the API test fails; once the fixtures are regenerated, the Frontend contract test fails until the types follow. The only change to `api-service/` is that one new test file (no source change).
3. **Playwright is extended (your choice at approval), with two facts you should know.** (a) The nightly e2e job has **failed every night since at least 13 Oct**: of ten cases, the four login cases and the dark-mode toggle pass, and five fail (the Dashboard one because the Dashboard opens on Category Trends, which Step 14 fixes as it touches the same page; the Settings and Transactions ones because the specs were written once, in commit `d349289`, and the pages have changed since). That is pre-existing and unrelated to Epic 13, so it is **not** repaired here; it will be offered as a separate task. (b) I cannot run Playwright on this machine, so Step 14 validates the new cases by running the existing workflow once on this branch through `workflow_dispatch`, which exercises the real compose stack with the new API.
4. **Baselines are recorded before anything changes** (Step 2): the number of passing tests, the `tsc` result and the exact set of existing `eslint` warnings (Epic 14 recorded five), so "no new warning" and "no existing test changed" are measurable.
5. **The browser check never touches live data or the live stack** (Step 15): a throw-away PostgreSQL with a seeded test user and sample accounts (a mismatch, a gap, a foreign-currency account, an overdrawn account, two same-named accounts, 14 deposit accounts), the API run from the working tree on a free port, and the built frontend served statically with a `config.js` pointing at it. The running containers on ports 8787 and 7878 are not used or changed.
