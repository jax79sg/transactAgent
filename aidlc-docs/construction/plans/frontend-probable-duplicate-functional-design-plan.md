# Functional Design Plan — Frontend Unit: Probable Duplicate Statement Detection (Epic 14)

Unit: Frontend (Unit 4). Scope: a nav badge, a panel on the Review page, a comparison page shared by two entry points, the override action, the "probable duplicate of <statement>" link in the Ingestion run results, and a dropdown for enumerated settings on the Settings page. Technology-agnostic: components, state, flows and wording; file layout and test code are Code Generation.

**No open questions.** The behaviour was fixed by the approved stories (including the Question 1 = C amendments), the requirements, and the API design; what remains is layout, wiring and wording, and each choice below follows from those or from how this app's screens are already built (I read the Review, Ingestion, Settings and NavBar code first). The table gives the reasoning so you can overrule any row at approval.

## A correction to something I told you earlier

At API Functional Design I said the Settings page already shows an enumerated setting as a dropdown. **It does not.** Every setting is edited in a plain text box with a hint such as "one of: false, true". The detection switch is an enumerated true/false setting, so as built it would be typed by hand. This stage therefore adds a dropdown for enumerated settings (a small change that also improves the one existing enumerated setting, which takes `low`, `medium` or `high`), and the API plan and the Application Design note that repeated the claim are corrected with a dated remark.

## Design decisions made and explained (not asked), with reasoning

| Topic | Decision | Why this isn't a question |
|---|---|---|
| **A second nav badge, beside the existing one** | A new count badge on the Review link next to the existing amber one, in a different colour (violet, with a dark-mode variant), hidden at zero, with an accessible label such as "3 duplicate statements awaiting review". Polls the pending-pair count every 30 seconds like the existing badge, mounted once in the nav, and is refreshed immediately by any action taken in the panel. | The approved Workflow Plan said "a badge beside the existing Review badge", and the existing badge's number means recategorization items; folding duplicates into it would change what that number means (NFR-PD-6). A distinct colour tells the two apart without reading. |
| **Where the panel sits, and how much room it takes** | A bordered section on the Review page below the Category Disagreements section and above the proposals table (so the three review flows sit together, and the backup status stays first). It is always present but compact when idle: a single line showing when detection last checked and a "Check again" button; or, when detection is switched off in Settings, "Duplicate detection is switched off" with a link to Settings. | Same "visually separate bordered section" convention as the backup panel and the disagreement table. Always showing the one-line state is what lets an empty panel say *why* it is empty (the API reports whether detection is on). |
| **The panel's groups** | Up to three headed groups, shown only when non-empty: "Awaiting your decision" (pending pairs, information-only ones included), "Being removed" (removal in flight), and "Removed in the last 24 hours". While any removal is in flight the panel refreshes every 3 seconds (the same as the Ingestion page's active-run poll, because the user is waiting for it); otherwise it refreshes only after the user's own actions. | The API's list has exactly these groups (AR-39). A pair leaves "pending" as soon as the deletion commits, so without the third group a finished removal would vanish before the user saw it complete. |
| **A pair's row** | Shows the copy to **keep** and the copy proposed for **removal**, each with file name, bank, period and transaction count, and the number of manual corrections on each; links "View comparison"; and the actions. A pair where removal is **not** offered (Question 1 = C) shows a clear note, "These statements differ in size, so this is listed for information only", with only "View comparison" and "Not a duplicate — dismiss" and **no remove action**. A stale pair (a statement no longer exists) says so and offers dismiss only. | Stories US-14.5 and the Question 1 = C amendment. Labels come straight from the API; nothing is recomputed in the browser. |
| **Removal confirmation** | "Remove duplicate…" opens a **modal dialog** (the same dialog component the Settings page already uses to confirm a change). It states exactly what will be permanently deleted: the transactions, statement sections, recategorization jobs and proposals, categorization disagreements and recurring-payment matches, and that the embeddings are removed too; how many transactions exist **only on this copy** and will be lost; how many **manual corrections** on it will be lost; and that the Drive file is left alone. The destructive button is worded "Delete permanently" and is disabled while the request is in flight. It sends the hash and the exact correction count the dialog showed. | FR-PD-10/12, NFR-PD-3, US-14.6, and the Question 1 = C amendment. Using the existing dialog keeps the app's confirmation behaviour consistent. |
| **When the confirmation is out of date** | If the server answers that the numbers changed since the user looked (or the pair was decided, or removal is no longer offered), the dialog closes, the list refreshes, and a plain message says what happened ("The corrections on this copy changed since you looked. Please review again."). Nothing is deleted. | The API's stale-confirmation guard (AR-42) is only useful if the UI turns it into a clear next step rather than a raw error. |
| **The comparison is a page, not a dialog** | A route, `/duplicates/<comparison id>`, behind the same login as every page, opened from two places: the "probable duplicate of …" link in the Ingestion results and "View comparison" in the panel. Back returns to where the user came from. | A page can be deep-linked, works with the browser's back button, and is simpler to use on a phone, which NFR-PD-8 requires; a dialog would be cramped with two tables. |
| **Comparison layout** | A heading and a state banner (skipped, removed, waiting for the next run, ingested at your request, or the pair's state); the stored reason; the headline figures (transaction counts, periods, how many matched). Two side panels, side by side on a wide screen and stacked on a narrow one, each titled by role ("This file" and "The statement it matches" for a skipped file; "Earlier ingested" and "Later ingested" for a pair), each a small table of up to 10 rows (date, description, amount, currency) ranked largest first. Every row carries a text marker, "Also on the other statement" or "Only on this one", plus a subtle tint, so meaning never depends on colour alone. | US-14.2 (the two snapshots side by side, each row marked; up to 10, largest first) and NFR-PD-8. The rows are ranked independently on each side, so matching rows are identified by their marker, not by position. |
| **Override** | In the comparison, when the API says it can be overridden, a button "Not a duplicate — ingest it". For a **skipped** file it is one click. For a **removed** copy it first shows an inline warning that the file will be ingested on the next run and that the corrections that sat on it are not restored, and needs a second click. After it succeeds the banner changes to "Will be ingested on the next ingestion run" with a link to the Ingestion page; if a statement with that file's hash exists it says "Ingested at your request". | US-14.3 and AR-44. A removed copy is the case with real consequences, so it gets the extra step; a skipped file is recoverable and gets none. |
| **Ingestion results** | The outcome cell for a skipped-probable-duplicate file reads "Probable duplicate of <file name> (<bank>, <period>)" and is a link to its comparison. Other outcomes are unchanged. The outcome type gains the new value (the closed type that would otherwise reject it). | US-14.1/14.2/14.4, A-PD-3. A file remembered from an earlier run appears the same way in a later run. |
| **One place to format a statement label** | A single helper builds "<file name> (<bank>, <period>)" (falling back to bank and period when there is no file name, and to "a statement" when there is nothing), and a period like "2 Jun to 30 Jun 2026". Month names are written out in the helper rather than taken from the browser's locale, so the same text appears everywhere and in the tests. | A-PD-3, and keeps the Ingestion page, the panel and the comparison from drifting. |
| **Settings page** | Enumerated settings are edited with a **dropdown** of their allowed values instead of a text box (the existing test id is kept on it); "Duplicate Statements" is added to the page's category order, after "Ingestion". The detection switch's own description (from the API) already says to enable it only after the accuracy check and that it takes effect when the worker restarts, and the existing save confirmation shows the restart guidance. | The correction above. The existing page already groups by category and appends unknown ones; adding it to the order list is deliberate placement. |
| **Error wording** | One small mapping from the API's stable error codes to plain messages: already decided, removal not offered, removal already requested, a statement no longer exists, confirmation out of date, not a skipped file. Unknown errors show the server's message. | The API gives one consistent error shape (Error Shape); this keeps every duplicate action's failures readable. |
| **Server state and refresh** | All server data goes through the app's existing query library. Panel actions (remove, dismiss, override, check again) refresh the pair list, the badge count and the scan status together. No global store, no new context. | How every other review screen works. |
| **Contract with the API** | The endpoint paths are fixed here so the two units agree: list pairs, pending count, one comparison, remove, dismiss, override, scan status, re-check, all under `/duplicates` (listed in `frontend-components.md`; a dated note is added to the API design). Request and response field names are camelCase; query parameters are converted to snake_case by the existing client. | The API design deferred exact paths to this stage. |
| **Theme, phone, accessibility** | Every new element has its dark-mode classes; tables scroll horizontally rather than overflowing the page; the two comparison panels stack on a narrow screen; buttons and links are comfortably tappable; status is conveyed in words as well as colour; the dialog traps focus (it is the same dialog component). | NFR-PD-8, US-14.2 ("legible and usable in light and dark, on a phone or desktop"). |
| **Tests (outlined for Code Generation)** | Component tests in the existing style (mocked API modules): the badge (hidden at zero, shows a count, refreshes after an action); the panel (each group, the idle and detection-off lines, an information-only pair has no remove action, a removal in flight polls and a finished one appears under "removed"); the confirmation dialog (shows each count, sends the shown correction count, handles an out-of-date answer); the comparison page (each state, marker text, override one-click versus two-click); the Ingestion link; the Settings dropdown (and that existing text-input settings still use a text box); the label and period helper as plain unit tests. | The project's established test layout; the e2e specs are out of scope for this stage. |
