## Findings from reading the code that shape this plan

1. **A file's writes are not actually atomic today.** `_process_one_file` flushes but only `update_run_progress` commits, and `_process_run` catches any unexpected exception and calls `fail_run`, which **commits**, partial writes of the in-flight file included (statement row, some transactions, and now accounts and sections). Because the statement's content hash is then recorded, that file would be skipped as a duplicate forever, leaving partial data. WR-49's "no orphan account or section if a file fails" depends on a rollback that does not exist. Step 7 adds `db.rollback()` before `fail_run`; earlier files are unaffected because each commits at its own end.
2. **The reingest must not be undone by worker startup recovery.** `main.recover_stale_state()` marks any queued or running ingestion run `failed` when a worker process starts. If the user restarts the worker while the backfill's reingest run is `running`, that run is failed (the normal-run fallback in the Functional Design then applies). The tool's runbook and its refusal messages say so; no code change to the poll loop.
3. **`session_scope()` commits on clean exit and rolls back on exception**; the CLI uses it the same way the poll loop does, and attaches the existing `DbLogHandler` so the reingest's log lines appear on the Ingestion page like any run.
4. **The test suite builds its schema with `Base.metadata.create_all` against `postgres:16-alpine`** and mocks external clients at their module boundary; this plan keeps that convention (real PostgreSQL, Drive/Gemini/OpenRouter/Qdrant mocked).
5. **No new dependency and no image or compose change** are needed (`python -m ingestion_worker.backfill ...` runs from the existing image), matching the approved Functional Design, so Infrastructure Design stays skipped.

## Steps

1. [x] **Business Logic Generation — extraction schemas** — modify `ingestion-worker/src/ingestion_worker/extraction/schemas.py`: add `RawAccountSection` (`account_identifier`, `account_type`, `currency`, `closing_balance`, `closing_balance_date`, `transactions`) and revise `RawExtractedStatement` to carry `sections`. Parsing is **lenient by design** (WR-44): a reply with no sections but a flat `transactions` list is wrapped as one section; an unknown or missing `account_type` becomes `unknown`; a malformed `closing_balance` or `closing_balance_date` becomes null instead of failing validation; an identifier given as a number is read as text. A read-only `transactions` property returns the flat list across sections, so existing readers keep working. No new field can make validation fail.
2. [x] **Business Logic Generation — extraction prompt** — modify `extraction/prompts.py` to the sections shape and WR-45's guidance (new section only for a clearly separate account, otherwise one section; identifier exactly as printed; account type; closing balance only for savings/current accounts, negative if overdrawn; every existing rule applies within each section; balance lines still never become transactions).
3. [x] **Business Logic Generation — extraction service** — modify `extraction/service.py` per WR-44/46/47: section currency fallback (WR-2 failure unchanged when neither exists); whole-document day/month swap detection across every section's transaction dates and closing dates; per-section chronological ambiguous-date correction; document-wide balance-line exclusion, future-date drop, and statement-date validation; per-section closing-date validation with fallback to the validated `statement_date`, else the balance pair is dropped and logged; a section with neither transactions nor a closing balance is dropped; zero transactions across the **whole** statement is still the WR-1c failure; confidence gate unchanged.

[x] **Business Logic Generation — Account Resolver** — create package `ingestion-worker/src/ingestion_worker/accounts/`: `normalize.py` (pure: `bank_key`, identifier normalization, default account name — WR-48, with the live bank names as test data), `repository.py` (key lookup, create account with its first key), and `service.py` (`resolve_sections`: key per section, lookup or create, collapse same-account sections keeping the first non-null closing balance with a warning, type rules WR-50, run-log lines — WR-49). No external calls.

[x] **Business Logic Generation — Duplicate Detection** — modify `duplicate_detection/service.py`: add `record_statement_accounts(db, statement, resolved_sections)` writing one `StatementAccount` per section (closing balance pair included) and returning the rows keyed for linking; `record_processed` and the hash check are unchanged.

Also add the **rollback fix** from Finding 1: `db.rollback()` before `fail_run` in `_process_run`'s unexpected-exception path, so a file that fails midway leaves nothing behind.

[x] **Business Logic Generation — Backfill Tool** — create package `ingestion-worker/src/ingestion_worker/backfill/` implementing WR-52..WR-56: `export.py` (per-table JSON-lines export using the database's own `to_jsonb(row)` so every column round-trips exactly; manifest with row counts and SHA-256; a single repeatable-read snapshot; upload; **download-back verification** against the manifest and the snapshot's live counts), `service.py` (wipe set = statements with no sections and a PDF still in Drive; pre-flight refusals; dry run; typed confirmation; single-transaction wipe in BR-36 order after detaching `ingestion_run_files.bank_statement_id`; vector-collection recreation with retry; reset kept statements' transactions to `embedding_status = 'pending'`; reingest as an ordinary run created already `running` and driven through `process_run`), `corrections.py` (capture manual corrections from the **backup artifact**, restricted to the wipe set; multiset matching on (content hash, date, amount, direction, description); direct writes, no recategorization jobs; idempotent), `restore.py` (manifest check first; typed confirmation; replace the backed-up tables in foreign-key order in one transaction using `jsonb_populate_recordset`; re-attach `ingestion_run_files` links; reset restored transactions to `pending`; recreate the vector collection), `report.py` (the WR-56 report with per-statement section counts, printed and saved beside the backup), and `__main__.py` (commands `run`, `finish --backup`, `restore --backup`, and the read-only `check-extraction` of step 10; applies migrations under the existing advisory lock first, attaches `DbLogHandler`, refuses to run non-interactively when a typed confirmation is needed).
