## Approach notes (stated up front)

1. **The matching rule is a pure module with no I/O** (`duplicates/matching.py`), so the property-based tests are cheap and the same function serves the pipeline, the scan, `check-duplicates` and the dry run (NFR-PD-7). Everything database-facing is a thin layer over it.
2. **Fail open at check 2** (WR-62). The judge call in the pipeline is wrapped so any exception logs a warning and a run-log line and the file ingests as today. A test proves a raising detector does not fail the file.
3. **One delete helper** (WR-68). The Backfill Tool's `perform_wipe` SQL moves into `duplicates/cascade.py::delete_statements`, which the backfill and the Statement Removal Handler both call. The existing backfill tests (counts, order, atomicity) must pass **unchanged**, which is the proof the move is behaviour-neutral. The helper also returns the removed transaction ids, captured **before** deleting.
4. **Setting-driven code reads `settings` at call time**, not import time, so tests can patch it; the three values are validated by pydantic bounds (a bad value stops the worker starting, WR-57).
5. **Raw SQL inserts supply Python-side defaults** (the Database contract): the worker writes pairs, jobs and known files through the ORM, so ORM defaults apply; the backfill's restore uses `jsonb_populate_recordset` with whole rows, which is unaffected.
6. **`process_run` gains a keyword, `backfill_mode`** (default false). In that mode check 2 runs whatever the switch says, and a different-size match is **not** skipped (WR-62, WR-69). Nothing else about `process_run` changes, so the Backfill Tool still drives the ordinary pipeline.
7. **Live data is not touched by this unit's tests or verification.** Everything runs against disposable containers. Running `check-duplicates` against the real database is part of Build and Test and needs its own go-ahead (the CLI applies migrations at start).
