## What your real data says (read-only run of the candidate rule, 2026-10-04)

Application Design carried "calibrate the matching tolerance and thresholds against the live statements" to this stage. I ran the candidate rule read-only over all **172 statements and 6,667 transactions** (11 bank keys). Nothing was changed; the working copy of the data was deleted afterwards, and only counts and ids were looked at.

- Only **four** pairs of statements share even one transaction, among everything that has the same bank and an overlapping period: the **UOB June pair** (5 of 5), the **Trust June pair** (8 of 8, spelled differently), and the **two CIMB look-alikes** (1 of 1 each, one-transaction statements).
- There is **nothing in between**: no pair is partly alike. A threshold anywhere from 50% to 100% gives the same four pairs, so 80% sits in a wide empty gap, and the small-statement gate (fewer than 3) is what separates the CIMB pairs from the June pairs. NFR-PD-1 holds on this data: both June pairs flagged, the CIMB look-alikes not, nothing else.
- In both genuine pairs **every description was identical** across the two copies (13 of 13). So the real data shows no wording drift between two reads of the same PDF, and the tolerance below is precautionary rather than measured. A looser description match changed no verdict.

This is a prototype run on today's data. The real accuracy gate remains the `check-duplicates` command in Build and Test.

## Design decisions made and explained (not asked), with reasoning

| Topic | Decision | Why this isn't a question |
|---|---|---|
| **Settings** | `duplicate_detection_enabled` (default **off**), `duplicate_match_ratio` (default 0.80, allowed 0.50 to 1.00), `duplicate_min_transactions` (default 3, allowed 1 to 50). Read at worker startup like every worker setting; out-of-range values stop the worker starting with a clear message. The switch gates only **new judgments**: the check after extraction and the pair scan. The remembered-file lookup, removal jobs, and the Review panel keep working when it is off. The Backfill Tool's reingest and `check-duplicates` always apply the rule, since each is an explicit operator action. | Approved defaults (Q2, Q3, Application Design). Below 0.50 the rule would start flagging statements that are plainly different. Honouring decisions already made (a removal, an override) must not depend on a switch. |
| **Matching is one-to-one** | A transaction on one side matches **at most one** on the other. A match needs the same **date, amount, direction, and currency**, and a description that matches by the rule in the next row. Within a group of same date, amount, direction, and currency, descriptions are paired best-first, so two identical purchases on one day are not counted twice. | Stops two identical coffees on a day from matching one coffee on the other statement and inflating the ratio. |
| **Description tolerance** | A description matches when it is equal after case-folding and collapsing whitespace, **or** when its similarity to the other is at least **0.85**. The 0.85 is a fixed constant, not a setting. Reference codes are **not** stripped (the recategorization code strips them for a different purpose; here two same-day same-amount purchases that differ only by reference should stay distinct). | FR-PD-3 requires tolerating small wording differences (A-PD-2). The live data shows none, so this is a narrow safety margin, and a fixed constant avoids a fourth setting nobody can calibrate. A looser match changed no verdict on 6,667 transactions. |
| **The ratio and the threshold** | `ratio = matched / the smaller side's transaction count`, and a pair is a candidate when `ratio >= duplicate_match_ratio`. | FR-PD-3 and A-PD-2, as approved. See Question 1 for the one consequence of "smaller" worth a decision. |
| **Period overlap** | Each statement's period is the earliest to the latest transaction date it holds, inclusive. Two periods overlap when those ranges intersect. | The live data has no period columns; this is derived and was exact for every real pair (identical ranges). Q2 chose "same period", not partial overlap, but a statement re-issued with a trivially shifted range should still count, and the 80% test on transactions protects against consecutive months. |
| **Same account, when known (A-PD-1)** | If **both** sides have account identifiers, they must share at least one (identifier, currency); with none shared they are different accounts and nothing is flagged. If either side has none (every statement before the Account Balance backfill), this test does not apply. For a held statement the identifiers are those of its sections' accounts at the same bank key. | Directly A-PD-1. Comparing a multi-account statement's transactions all together and requiring one shared account is the simplest rule that never calls two different accounts the same. |
| **Small statements (FR-PD-4)** | If either side has **fewer than `duplicate_min_transactions`** transactions, the ratio test still applies **and** both sides must have a shared account whose closing balance and closing-balance date are identical. Before the backfill nothing has identifiers, so small statements are never flagged, which is what keeps your CIMB look-alikes out. | As approved (Q3 = A): "also" means in addition to the transactions matching. |
| **Which held statements are candidates** | Same bank key (the Account Resolver's normalizer, so Trust's two spellings still meet) and overlapping period; pairs the user dismissed are excluded; an incoming file the user overrode is exempt. A statement with no bank name is never compared. Of several candidates the best wins (most matches, then the earlier ingested). | FR-PD-3, A-PD-5, FR-PD-7. A missing bank name cannot be matched to anything, so skipping it is the safe reading. |
| **The comparison (evidence)** | The side named *earlier* is the earlier-ingested statement; for a skip, the held statement is *earlier* and the incoming file *later*. Each side stores its label (file name, bank, period), and its **10 largest transactions by amount** (ties: earlier date, then description for a stable order), each marked as matched or not by the same matching used for the verdict. The held side's file name comes from the run file that processed it, and is stored empty if none can be found. | FR-PD-5 and Clarification Q1. Using the verdict's own matching for the markers guarantees the rows that line up in the view are the rows that were counted. |
| **Check 1 (before extraction), always on** | After the exact-bytes check, look up the file's hash. `probable_duplicate` or `confirmed_duplicate`: record the run file as skipped with the stored comparison, count it as skipped (never a failure, BR-52). The file has been downloaded (it must be, to be hashed) but is not extracted: no Gemini call. `overridden`: continue to extraction and exempt the file from check 2. None: continue. | FR-PD-8, FR-PD-7, NFR-PD-2. |
| **Check 2 (after extraction, before accounts)** | When detection is on and the file is not overridden, judge it against the held statements. On a probable duplicate, write the comparison and a `probable_duplicate` remembered file and record the run file as skipped, **inside the file's own savepoint**, so a skipped file creates no statement, section, transaction, or account (FR-PD-1). If the detector itself raises, it **fails open**: a warning and a run-log line, and the file ingests as it does today. | A failed duplicate check must never block a statement from being ingested; wrongly ingesting a duplicate is today's behavior and the pair scan will find it, whereas a file that cannot ingest is a new failure mode. |
| **Two copies in one run (A-PD-7)** | The first is persisted before the second is judged, so the second is flagged against it. | The per-file savepoint already makes the first visible to the second. |
| **Run log** | Every skip writes a run-log line naming the file, the statement it matches, and the reason ("8 of 8 transactions match"). | The existing run-log mechanism shows it live on the Ingestion page. |
| **Pair scan: when it is due** | Only when detection is on, and one of: no scan has completed; the ratio or minimum a past scan used differs from the current settings; a re-check was requested after the last scan started; or a statement was added after the last scan started. | The last condition covers statements ingested while detection was off, and the backfill's re-created statements. A scan is cheap (11 bank groups, a few hundred comparisons), so over-scanning costs nothing and under-scanning would hide a duplicate. |
| **Pair scan: what it writes** | For each pair found: insert a pair (with its comparison and the proposed kept copy) if no row exists for those two hashes; refresh a `pending` pair's proposal; leave `dismissed`, `removed` and `superseded` alone; mark a `pending` pair `superseded` when its statements are no longer both held. Files whose remembered state is `overridden` are excluded on either side. Three copies of one statement make three pairs, and removing one supersedes the stale ones. | BR-44 and A-PD-5. |
| **The keep proposal** | The copy carrying manual category corrections; else the earlier-ingested one (by ingestion time, then the smaller hash, so it is deterministic). Computed once by the worker, stored on the pair, and refreshed on re-scan. | FR-PD-11 and the Application Design rule that the API never recomputes it. |
| **Poll loop** | Seven branches in the order set at Application Design (removal third, pair scan sixth). At startup, a removal job left `running` is marked `failed` ("interrupted; nothing was deleted"), since the deletion commits atomically with the move to `embeddings_pending`; a job in `embeddings_pending` is simply picked up again. | Application Design carry-forward 4. |
| **Removal: re-verification** | Before deleting, check: the pair is still `pending`; the statement to remove exists; **the statement to keep still exists** (never delete the last copy); the pair's stored keep-proposal still names the *other* hash (a re-scan after the user confirmed may have changed it); and the manual corrections on the copy being removed are not more than the user acknowledged. Any failure marks the job `failed` with a plain reason and deletes nothing. | NFR-PD-3. The "keep still exists" and "proposal unchanged" checks are two ways a stale confirmation could otherwise delete the wrong thing. |
| **Removal: the transaction** | In **one** database transaction: delete the statement and everything depending on it (the shared dependents helper), insert the removed file's hash as a `confirmed_duplicate` remembered file, mark the pair `removed`, and move the job to `embeddings_pending` with the removed transaction ids and the deleted counts. | BR-46. Doing the remembered-file and pair bookkeeping in the same transaction means the file can never be re-ingested in the gap before the embeddings are cleaned. **A small refinement of the Database design:** it said a pair becomes `removed` when the job completes; here it becomes `removed` when the database deletion commits, because from the user's point of view the statement is gone then. A one-line dated note is added to the Database lifecycle. |
| **Removal: embeddings** | Delete the removed transactions' vectors with up to **5 attempts inside one poll cycle**, waiting 1, 2, 4 and 8 seconds between them, counting each in `embedding_attempts`. Success: `completed`. All five fail: `embeddings_failed` with a reason, parked. A job found in `embeddings_pending` at a later cycle (for example after a restart) resumes the same way. | The Database design has no "last attempt" timestamp to space retries across cycles, and a blocked single-threaded worker for about 15 seconds is acceptable. Orphaned vectors are harmless: similarity candidates are looked up by id and a missing transaction drops out. |
| **One delete helper** | The Backfill Tool's wipe SQL moves into a shared helper that deletes a list of statements, returns the removed transaction ids and per-table counts, and detaches their run files; the backfill's wipe becomes a thin caller (counts unchanged) and the removal handler calls it for one statement. | Application Design carry-forward 5 / BR-51: one implementation of the dependents list. |
| **Vector store** | New `delete_embeddings(collection, entity_ids)`, returning true or false and never raising, like every function in that client; deleting an id that is not present is not an error. | Same convention as the rest of the client; makes a retry safe. |
| **Backfill: always applies the rule** | `run`'s duplicate handling and its reingest apply the rule regardless of the switch. | An explicit operator command; Q7 = A asks the backfill itself to resolve the pairs. |
| **Backfill: dry run and `check-duplicates`** | `check-duplicates` (read-only; no Drive or Gemini calls) prints every pair the rule flags, with its reason, the transaction counts, the copy it would keep, and the manual corrections on each. It **also lists every near miss**: a pair with the same bank, an overlapping period and at least one shared transaction that was *not* flagged, with the reason (below the ratio, a small statement without matching identifiers and balances, different accounts). The dry run adds the pairs it will skip and the copy it keeps. | NFR-PD-1 is a human check on real data, and "the CIMB look-alikes are not flagged" can only be judged if the tool shows them and says why. This is exactly the list the prototype produced. |
| **Backfill: pre-registration scope** | A pair is pre-registered only when the copy to skip **is in the wipe set** (it will be re-read). The skipped copy gets a `probable_duplicate` remembered file pointing at the kept copy and reusing the pair's comparison. Pairs the user dismissed are not pre-registered; pending pairs the reingest resolves are marked `superseded`. A pair whose skip-copy is not wiped (its PDF is missing from Drive, or it is already converted) is left for the user's panel. | Pre-registering something that will not be re-read would do nothing, and a pair left alone stays visible. |
| **Backfill: corrections** | `finish` re-keys each captured correction whose statement was skipped to the **kept copy's hash** through the remembered file, following a chain if needed, then applies them. **The kept copy's own corrections win**: a carried correction is applied only to a transaction not already corrected, and is reported as superseded otherwise. | FR-PD-17. Never overriding a correction the user made on the kept copy is the safe merge, and it is consistent with FR-PD-11's "corrections on the removed copy are lost" only where there is a genuine conflict. |
| **Backfill: pre-flight and safety** | Refuses while any removal job is queued, running, or awaiting embedding cleanup. `finish` requests a pair scan when it completes. The completion report lists the skipped duplicates (file, what it matched, comparison available) and the corrections carried, superseded, and unmatched. | Application Design; the scan after `finish` covers small statements that become flaggable once identifiers exist. |
| **Backfill: backup and restore** | The backup also covers the four mutable new tables (remembered files, pairs, removal jobs, scan state); `restore` replaces their contents with the backup's. Comparisons and their rows are write-once evidence that nothing deletes, so they are **not** replaced: a comparison created after the backup simply stays, harmlessly. | `restore` has to undo the pre-registrations and the superseded pairs, and the new tables have no foreign key to anything restore deletes (BR-50). |
| **Errors** | Nothing in the poll loop raises out of a cycle: a failed scan is logged and retried at the next due cycle; a failed removal ends in `failed` or `embeddings_failed` with a reason. | The existing worker convention (WR-12 for backup). |

## Genuinely open question

### Question 1
The rule measures a match against the **smaller** statement (A-PD-2, approved). That has one consequence: if a new file **contains all of a smaller statement you already have, plus more transactions of its own** (for example, an interim statement is held, and the full-period statement arrives later), the match is 100% and the file is skipped as a probable duplicate, so the extra transactions are not ingested. The reverse case on two held statements is worse: the panel would propose removing a copy that has transactions the other does not.

Nothing like this exists in your 172 statements, so it is a precaution. The comparison view and the run result would show it (for example "5 of 5 match; this file has 30 transactions"), and you could override, but you would have to notice.

How should the app treat two statements of clearly different sizes where the smaller is wholly contained in the larger?

A) **Keep the approved rule, and make the difference impossible to miss.** Still flag it, but the reason text and the comparison view say prominently that the other statement is larger and has transactions the smaller one does not; and for a held pair, the removal confirmation states how many transactions exist **only on the copy being removed** and that they will be lost. Nothing is ever ingested twice; a person decides.

B) **Only flag statements of similar size.** Require the smaller side to be at least 80% as large as the larger (the same threshold, applied both ways). A file that is a much bigger version of a held statement is **not** flagged: it is ingested normally, so the overlapping transactions are counted twice until you notice, and the pair is not listed in the panel either.

C) **Flag it, but never propose removal.** Same as A at ingestion, but for already-held pairs of clearly different sizes the panel lists the pair for information only, with a "dismiss" action and no "remove" action, so removal is possible only when the two are the same size.

## Answer applied (2026-10-04)

**Question 1 = C.** Ingestion flags and skips a statement that wholly contains a smaller held one, as in option A (WR-60, WR-62), with the size difference stated prominently. For held pairs of clearly different sizes the panel lists the pair for information only, with a dismiss action and no remove action (WR-64). Three consequences resolved without asking, because each follows from C and has one sensible reading:
1. **"Clearly different sizes" reuses the match ratio in the other direction** (the smaller side has fewer than `duplicate_match_ratio` times the larger side's transactions), the same threshold option B described; there is no new setting.
2. **The worker stores the result on the pair.** The API must not recompute it, so `DuplicatePair` gains a required boolean `removal_allowed`. This **reopens the Database unit for one column** (a dated section is added to the Database code generation plan, pending approval; migration 0020 is unreleased, so it is reworked in place).
3. **The backfill's reingest never skips a different-size match**, so a larger statement's extra transactions are never silently dropped in the mode that otherwise resolves pairs automatically (WR-62, WR-69).
