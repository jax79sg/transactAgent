# Components — Bank Transaction Insights App

Architectural style: **Separate services** (Question 1 = B) — an **API Service** and an **Ingestion Worker Service**, both sharing one PostgreSQL-class database, plus a **Frontend** SPA. Components below are grouped by which deployable service owns them.

---

## Frontend

- **Purpose**: Rich single-page web application — the only surface the Account Owner interacts with directly.
- **Responsibilities**: Login screen; ingestion trigger + live progress/run history views; transaction table with filter/group/sort/export; manual category correction UI; dashboards (category trends, cash flow, bank breakdowns) with drill-down; category whitelist settings.
- **Interfaces**: Consumes the API Service's REST API (Question 4 = A) exclusively — never talks to the Ingestion Worker or database directly.
- **Stories covered**: All 24 (as the presentation layer for every capability).

## API Service Components

### Auth Component
- **Purpose**: Protect the entire application behind a single-user login.
- **Responsibilities**: Validate credentials, issue/validate session (e.g., session cookie or JWT), reject unauthenticated requests to any other API Service route.
- **Stories covered**: US-5.1

### Transaction Management Component
- **Purpose**: Owns all read/write access to transaction data on behalf of the user-facing UI.
- **Responsibilities**: List/filter/group/sort transactions; return a single transaction's detail (original + converted amount); apply manual category corrections and mark `category_source = manual`; trigger the retroactive-UNSURE-recategorization job (FR-5.4) after a correction; CSV export of the current filtered/grouped view.
- **Stories covered**: US-3.1, US-3.2, US-3.3, US-3.4, US-3.5, US-3.6, US-3.7
- **Addendum (2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9)**: `listTransactions`/`getTransaction` now also return each transaction's `embedding_status`, read directly from the Shared DB (FR-7, US-9.1). Read-only — this component never calls the Vector Store Client or the embedding endpoint itself; it only surfaces a field the Ingestion Worker's new Embedding Manager Component writes.

### Dashboard/Insights Component
- **Purpose**: Serve aggregate, SGD-converted financial insight queries to the Frontend.
- **Responsibilities**: Category-trend aggregation; income-vs-expense/cash-flow aggregation; bank-level breakdown aggregation; apply date-range/currency filters; surface approximate-conversion / excluded-transaction disclosures per transaction set.
- **Stories covered**: US-4.1, US-4.2, US-4.3, US-4.4, US-4.5, US-4.6

### Ingestion Trigger & Status Component
- **Purpose**: The API Service's side of the async ingestion workflow — never performs extraction/categorization itself.
- **Responsibilities**: Accept a "start ingestion run" request from the Frontend and enqueue a run record for the Ingestion Worker; expose run status/progress (for polling) and run history for past runs, including per-file outcomes and failure reasons.
- **Stories covered**: US-1.2, US-1.5
- **Addendum (2026-08-01, during Unit 3 NFR Requirements)**: also owns the Google Drive OAuth connect/callback handshake (US-1.1) — added retroactively since Unit 3 (Ingestion Worker) has no browser-facing interface of its own to run an interactive OAuth flow; see `construction/api-service/code/api-layer-summary.md` and `audit.md` for the full history.
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)**: The per-file outcomes it exposes gain a fourth value, **skipped as a probable duplicate** (distinct from the existing exact-duplicate skip, FR-PD-2), and each such run-file detail carries a link to its stored comparison and the matched statement's label, so the Frontend can show "probable duplicate of <statement>" (US-14.2). No new endpoint and no new behavior beyond reading the extra fields; run enqueueing is unchanged.

### Recategorization Review Component
- **Addendum (2026-08-02, Recategorization Review Panel feature — see `recategorization-review-application-design-plan.md`)**
- **Purpose**: Owns the human-in-the-loop review of proposed category changes that the Categorization Engine (Ingestion Worker) generates but doesn't auto-apply.
- **Responsibilities**: List pending proposals with enough context to judge them (candidate transaction, proposed category, match score/bucket, triggering correction); approve or reject a proposal individually or in bulk, writing the category directly to the transaction on approval; expose a pending count for the nav badge.
- **Interfaces**: New REST endpoints, consumed by the Frontend SPA's new Review page. Depends only on the Shared Data Store (reads/writes proposal rows and, on approval, the `transactions` table) — never calls the Ingestion Worker Service directly, matching this project's one hard architectural rule.
- **Stories covered**: US-6.4, US-6.5, US-6.6
- **Addendum (2026-08-16, Matching Precision Refinement feature — see `matching-precision-refinement-application-design-plan.md`)**: Also owns review of `CategorizationDisagreement` items (FR-MPR-9/10/11) — a distinct entity from `RecategorizationProposal` (two candidate categories, no triggering job), written by the Ingestion Worker's Categorization Engine, resolved here via pick-one-or-reject rather than approve/reject. The existing pending-count method now sums both entities' pending rows for one nav badge total. No bulk actions for disagreements (Design Decision 2) — each resolution is an individual, specific choice between two different categories.

### Backup Status Component
- **Addendum (2026-08-08, Nightly Transaction Backup feature — see `nightly-backup-application-design-plan.md`)**
- **Purpose**: Exposes the Ingestion Worker Service's nightly backup history/status to the Frontend, read-only.
- **Responsibilities**: Report the outcome of the most recent backup attempt (success, or failure with a failure category — `drive_connectivity` vs `other`) so the Review page's Backup Status panel can render the right message.
- **Interfaces**: New REST endpoint(s), consumed by the Frontend SPA's Backup Status panel. Depends only on the Shared Data Store (reads the new `backup_runs` table) — never calls the Ingestion Worker Service directly, matching this project's one hard architectural rule (same as the Recategorization Review Component).
- **Stories covered**: US-7.4

### Recurring Payments Component
- **Addendum (2026-08-08, Recurring Payments feature — Epic 8, see `recurring-payments-application-design-plan.md`)**
- **Purpose**: Owns the recurring-payments register, the human review side of the match workflow, and detection-suggestion triage.
- **Responsibilities**: CRUD for Recurring Payments (US-8.1); bulk CSV import with per-row error isolation (US-8.2); list/approve/reject pending matches (US-8.4); list, dismiss, or add-from detection suggestions (US-8.6); a status summary (due soon / overdue / pending / new suggestions counts) backing the Dashboard section and the nav badge (US-8.3, US-8.7).
- **Interfaces**: New REST endpoints under `/recurring-payments`, consumed by the Frontend SPA's Dashboard section. Depends only on the Shared Data Store — never calls the Ingestion Worker Service directly (same rule as Recategorization Review and Backup Status). Approve/reject writes are synchronous, direct DB writes (same precedent as Recategorization Review's approve/reject) — matching, trust-tracking, and detection remain exclusively the Worker's responsibility.
- **Stories covered**: US-8.1, US-8.2, US-8.3 (status data), US-8.4, US-8.6, US-8.7 (status data)

### Configuration Component
- **Purpose**: Manage user-editable configuration that isn't a secret.
- **Responsibilities**: List/add/rename/remove categories in the whitelist; validate that a category removal doesn't orphan existing transactions (block or require reassignment first).
- **Stories covered**: US-5.2
- **Addendum (2026-08-16, Configurable Application Settings feature — see `configurable-app-settings-application-design-plan.md`)**: Extended, not replaced — the same "manage non-secret user-editable configuration" charter now also covers the 35 in-scope application settings (Epic 10), not just the category whitelist. New responsibilities: list all in-scope settings with their current effective value, owning service, and standard/advanced classification (FR-CAS-1/2/3, US-10.1/10.2); validate a proposed new value against that setting's real type/range and, only if valid, write it to the new shared override-settings file (FR-CAS-4/5/8) — never the secrets-bearing root `.env`; record every successful write as a new `SettingChange` history row (FR-CAS-9, US-10.4); compute restart guidance for a just-changed setting — which container, the exact command, and (only for Ingestion-Worker-owned settings) a busy/idle read (FR-CAS-6/7, US-10.3, Key Design Resolution 2 below). Enforcement is allow-list-based, not denylist-based (see "Component Boundary Note" in the plan doc) — a request naming any of the 13 excluded secret/credential fields is rejected by construction, since those names simply aren't on the list `updateSetting`/`getSetting`/`listSettings` consult (NFR-CAS-2).

**Note**: Secrets configuration (US-5.3 — Google OAuth client, LLM API key, FX API key, DB credentials, JWT secret) remains environment-variable-based at container startup (NFR-4.1) and outside this component's reach entirely, even after the 2026-08-16 addendum above — both services still read their own required secrets from their own environment at boot and fail fast if missing. The addendum only moved the 35 *non-secret* settings from "env-var-only" to "editable via this component, env-var/override-file as the underlying mechanism."
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14)**: The in-scope allow-list gains three Ingestion-Worker-owned settings: **detection on/off** (default **off**, so the feature is switched on only after the accuracy evaluation, NFR-PD-1), the **match ratio** (default 0.80, Q2 = B) and the **small-statement minimum** (default 3, Q3 = A). They take effect, as every worker setting does, at the worker's next restart. No new responsibility — they appear on the Settings page through the existing catalog (the asserted entry count rises accordingly).
- **Amendment (2026-10-04, API Service Functional Design, AR-48)**: the catalog has no boolean type, so the detection switch is an enumerated `false`/`true` choice (shown as a dropdown once the Frontend adds one for enumerated settings; today every setting is edited in a text box, which an earlier version of this note wrongly said was already a dropdown, corrected 2026-10-04), in a new category "Duplicate Statements"; the catalog grows from 44 to 47 entries; and the Settings service now renders a non-overridden boolean in lowercase, which the switch would otherwise have shown as "True"/"False" and failed to match its own allowed values.

### Background Activity Component
- **Addendum (2026-08-18, Background Process Visibility feature — see `background-process-visibility-application-design-plan.md`)**
- **Purpose**: Read-only visibility into what the Ingestion Worker is doing right now and what it recently finished, for the two job types that have a real in-progress status today.
- **Responsibilities**: Report whether an ingestion run or recategorization job is currently `running` and, if so, which one (FR-BPV-2, FR-BPV-5, US-11.1/11.2); list recently-completed ingestion runs and recategorization jobs, most recent first (FR-BPV-3, FR-BPV-6, US-11.3). A narrower, purpose-built sibling to the existing `is_ingestion_worker_busy()` check used by the Configuration Component's restart guidance — that check only needs a boolean, this component needs job-type identification plus history, so it gets its own endpoint rather than overloading that one.
- **Interfaces**: One new REST endpoint, consumed by the Frontend SPA's nav bar indicator + detail panel. Depends only on the Shared Data Store (reads `ingestion_runs`/`recategorization_jobs`, both already written by the Ingestion Orchestrator/Categorization Engine) — never calls the Ingestion Worker Service directly, matching this project's one hard architectural rule (same as Backup Status, Recurring Payments, Recategorization Review).
- **Stories covered**: US-11.1, US-11.2, US-11.3

### Account Management Component
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13, see `account-balance-application-design-plan.md`)**
- **Purpose**: Owns the user-editable side of accounts — which accounts exist, what each is called, whether it is a deposit account, and its balance anchor.
- **Responsibilities**: List accounts with type, currency, anchor, and statement count (US-13.1's visible side); rename an account; merge one account into another — reassigning the absorbed account's statements to the survivor, requiring an explicit choice of which anchor survives when both have one, and refusing when the two currencies differ (US-13.2, A-6); correct an account's type (US-13.2, A-3); set or replace a deposit account's single active anchor, rejecting a non-numeric value or a future as-of date, and offering no anchor for non-deposit accounts (US-13.3, A-6, A-7). It never *creates* accounts from statements — that is the Ingestion Worker's Account Resolver Component's job; this component only edits what ingestion created.
- **Interfaces**: New REST resource endpoints under their own router, consumed by the Frontend SPA. Depends only on the Shared Data Store (reads/writes accounts and anchors; reads/updates `bank_statements`' account reference on merge) — never calls the Ingestion Worker Service directly, matching this project's one hard architectural rule.
- **Stories covered**: US-13.2, US-13.3
- **Addendum (2026-10-02, found at Database Functional Design — see `database-account-balance-functional-design-plan.md`, BR-35)**: A merge also re-points the absorbed account's `AccountKey` rows to the survivor, so a future statement that used to resolve to the absorbed account now resolves to the survivor — without this, a merge would only fix past statements. The whole merge (currency check, anchor choice, statements, keys, deleting the emptied account) is one all-or-nothing operation, and the schema only allows an account to be deleted once it has no statement sections, keys, or anchor.
  - **Scope change (2026-10-03)**: a merge re-points the absorbed account's **statement-account rows** (not statements), and is **refused when the two accounts appear together in any one statement** — a statement that lists both proves they are different accounts.

### Balance Component
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13, see `account-balance-application-design-plan.md`)**
- **Purpose**: Read-only computation of balances, the balance trend, and statement-vs-computed discrepancies for deposit accounts.
- **Responsibilities**: For a requested date (or a month, which it resolves to the month's last day, or today for the in-progress month, per A-5), compute each deposit account's end-of-day balance in its own currency from its anchor and transactions — forward or backward from the anchor date (FR-AB-7) — convert to SGD, and add up a combined total that names every excluded account and why (no anchor, FX unavailable — FR-AB-9, FR-AB-11, A-8); report the date through which transactions have been ingested (FR-AB-14); compute the same balance across a date range for the chart, with every plotted point equal to the single-date lookup (US-13.5); and list discrepancies between each statement's printed closing balance and the anchor-based balance on that statement's closing date (FR-AB-8, US-13.6). The core arithmetic is a **pure function**, kept separate from its I/O wrapper — the property-based-testing target (NFR-AB-4), following Currency Conversion's existing pure-decision/outer-I/O split.
- **FX as-of-date (Question 1 = A)**: reads only the existing `fx_rate_cache`, using the nearest earlier cached rate for the account's currency → SGD on or before the requested date. No exact-or-earlier rate means that account's balance is unavailable. A rate whose date differs from the requested date means the converted figure is marked **approximate**, mirroring the existing `conversion_is_approximate` concept for transactions. This component never calls an external FX service, so no new dependency is introduced between `api-service` and anything outside the database.
- **Computed on request**: nothing is precomputed, materialized, or stored — a replaced anchor or an account merge would invalidate it, and a corrected anchor must make a discrepancy warning vanish by itself (US-13.6).
- **Interfaces**: New REST endpoints under their own router, consumed by the Frontend SPA's Dashboard balance section. Depends only on the Shared Data Store (reads accounts, anchors, `bank_statements`, `transactions`, `fx_rate_cache`).
- **Stories covered**: US-13.4, US-13.5, US-13.6 (computation side)
- **Scope change (2026-10-03)**: an account's transactions are reached through their statement-account link, and its printed closing balances are the closing balances on that account's statement-account rows, so a multi-account PDF contributes one cross-check per account. Signatures and everything else above are unchanged.

### Duplicate Review Component
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)**
- **Purpose**: The API Service's side of probable-duplicate handling — shows the user what the Ingestion Worker found and records the user's decisions. It computes nothing about whether two statements match.
- **Responsibilities**: List the pairs of already-ingested statements awaiting a decision, each with its stored comparison, the copy the worker proposed to keep and the copy proposed to remove (FR-PD-9/11), the live count of manual corrections on each copy, and a confirmation preview of exactly what removal would delete (transactions and dependent rows, FR-PD-12); give the pending-pair count for the nav badge (same shape as the existing `GET /proposals/pending-count`); return one comparison by id for the shared comparison view (FR-PD-6); **confirm a removal** by writing a removal job that carries what the user acknowledged (FR-PD-10/14); **dismiss** a pair, remembering it (FR-PD-10, A-PD-5); **override** a skipped file by writing the "not a duplicate" decision against its content hash (FR-PD-7, takes effect on the next ingestion run, A-PD-4); report a removal's pending/done/failed status; and let the user ask for a re-check of the held statements.
- **Interfaces**: New REST router under the same authentication as the existing API (NFR-PD-8), consumed by the Frontend SPA. Depends **only on the Shared Data Store**. It never connects to the vector store and never calls the Ingestion Worker (NFR-PD-4): removal is requested through a job row and executed by the worker, the same way manual corrections hand off to the worker's recategorization job.
- **Design rule**: the keep/remove proposal is computed **once, by the worker** (Probable Duplicate Detector Component), stored on the pair, and only displayed here; this component never recomputes it. A rule that existed in both services could drift, and a mismatch would delete the wrong copy.
- **Stories covered**: US-14.2, US-14.3, US-14.5, US-14.6 (request/decision side)
- **Amendment (2026-10-04, API Service Functional Design, see `api-service-probable-duplicate-functional-design-plan.md`, AR-38..AR-50)**: the panel's list has three groups, not one — pending pairs (information-only ones included), pairs whose removal is in flight, and pairs removed in the last 24 hours (the Database design moves a pair to `removed` when the deletion commits, so a pending-only list would make a removal vanish before the user saw it finish). The badge counts pending pairs with no active removal job. Confirming a removal requires the hash and the exact manual-correction count the user was shown, and the preview's `onlyOnRemovedCopy` is derived from the stored comparison (removed side's count minus matched count), so the API holds no copy of the matching rule. The scan-status endpoint also reports whether detection is switched on, so an empty panel can say so. Run-file details gain the comparison id and a structured matched-statement label.

## Ingestion Worker Service Components

### Drive Connector Component
- **Purpose**: All interaction with Google Drive.
- **Responsibilities**: Perform/refresh OAuth authentication; list PDF files in the configured folder; download file bytes for processing.
- **Stories covered**: US-1.1, part of US-1.2
- **Addendum (2026-08-08, Nightly Transaction Backup feature)**: Adds write-side operations against the separate, dedicated backup Drive folder (distinct from the ingestion source folder): ensure the `backup` subfolder exists (creating it if needed), upload a file, list files in that subfolder, and delete a file. Reuses the same shared OAuth credential and the existing retry/transient-error pattern already used for list/download. Still "all interaction with Google Drive" — no new component needed.

### Backup Manager Component
- **Addendum (2026-08-08, Nightly Transaction Backup feature — see `nightly-backup-application-design-plan.md`)**
- **Purpose**: Owns the nightly transaction backup capability — a time-triggered concern, distinct from the queue-triggered Ingestion Orchestrator.
- **Responsibilities**: Detect when a backup is due (scheduled time reached, or a missed backup needs to catch up per FR-8); export a full snapshot of all transactions to CSV; upload it via the Drive Connector Component to the dedicated backup folder's `backup` subfolder; enforce retention (keep the 7 most recent, delete older, scoped only to this feature's own files); record the outcome (success, or failure with a failure category) for the Backup Status Component to read.
- **Stories covered**: US-7.1, US-7.2, US-7.3, US-7.4 (status-recording side)

### Duplicate Detection Component
- **Purpose**: Prevent reprocessing of already-imported statements.
- **Responsibilities**: Compute a hash of each downloaded PDF's raw bytes; check it against the processed-statements record; record the Drive file ID + hash once a statement is successfully processed.
- **Stories covered**: US-1.4
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13)**: The step that records a successfully processed statement now also stores the statement's account reference (from the Account Resolver Component, below) and its printed closing balance with the date it applies to (FR-AB-5). Whether the as-extracted account type is also kept per statement, in addition to the user-correctable type on the account itself, is a Functional Design (Database unit) decision. The duplicate check itself (content hash) is unchanged.
  - **Scope change (2026-10-03)**: the closing balance no longer lives on the statement. Recording a processed statement now also records one **statement-account row per account section** (the section's account and, if printed, its closing balance and date), and each persisted transaction is linked to its section.
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14)**: Gains one step, performed **after** the existing exact-bytes check and **before** extraction: look up the file's content hash among the **remembered files** (FR-PD-8). A hash remembered as a probable duplicate or as a removed duplicate is skipped without a Gemini call (NFR-PD-2); a hash the user overrode proceeds to extraction and is exempt from similarity flagging (FR-PD-7). This lookup is **always on**, even when detection is switched off, because it honours decisions the user already made. The exact-duplicate check itself is unchanged (NFR-PD-6).

### Statement Extraction Component
- **Purpose**: Turn a PDF (bytes) into structured transaction rows.
- **Responsibilities**: OCR fallback for scanned/image PDFs; layout-adaptive, LLM-assisted parsing to identify transaction date/description/amounts, bank name, and currency; flag a statement as failed/needs-review when extraction confidence is too low.
- **Stories covered**: US-1.3
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13)**: The extraction schema and prompt gain three new, optional statement-level fields: an account identifier (the account number or its last few digits), an account type (deposit account / credit card / unknown), and the statement's printed closing balance with the date it applies to (FR-AB-2, FR-AB-4, FR-AB-5). All existing safety nets — day/month-swap and ambiguous-date correction, balance-line exclusion from the transaction list, future-date drop, confidence gating — stay unchanged (NFR-AB-3); the closing balance is read into its own field and is never a transaction. The new fields are optional at the schema level, so a statement missing any of them still ingests (A-2, A-3).
  - **Scope change (2026-10-03, Ingestion Worker Functional Design clarification Q1 = B)**: those fields are now per **account section**, not per statement. A parsed statement is `{bankName, statementDate, confidence, sections: [{accountIdentifier?, accountType?, currency, closingBalance?, transactions}]}`; a single-account PDF is one section, and a reply that returns one flat transaction list is accepted as one implicit section. Day/month-swap detection, future-date drop, balance-line exclusion, statement-date validation, and confidence gating still run across the whole document; the chronological ambiguous-date correction runs per section.

### Probable Duplicate Detector Component
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)** — deliberately a different component from the Duplicate Detection Component above: that one compares **bytes before extraction**; this one compares **extracted transactions after extraction**.
- **Purpose**: Decide whether one statement is probably the same statement as another already held, and keep the evidence.
- **Responsibilities**:
  1. *The matching rule, as pure functions* (the property-based-testing targets, NFR-PD-7): match transactions between two statements **one-to-one** (each transaction on one side matches at most one on the other, on date, amount, direction, and description with the wording tolerance, FR-PD-3), compute the match ratio against the **smaller** statement, test period overlap, apply the small-statement gate (fewer than the minimum is never flagged on transactions alone, FR-PD-4), produce the verdict; select the **comparison snapshot** (the 10 largest transactions by amount per side, ties earlier date first, each marked "also on the other statement" or "only on this one", FR-PD-5); and choose which copy of a pair to keep (the one carrying manual corrections, else the earlier-ingested, FR-PD-11).
  2. *Judging an extracted statement* against the held statements: candidates are those with the same normalized bank key (the Account Resolver's normalizer, so the Trust pair's two spellings of the bank name still meet) and, when both sides have account identifiers, the same account; pairs the user dismissed are excluded; the best candidate wins. Read-only until a skip is recorded.
  3. *Recording a skip*: writes the comparison and the remembered-file record (state "probable duplicate", pointing at the matched statement by content hash). Nothing else is written, so a skipped file creates no statement, section, transaction, or account (FR-PD-1).
  4. *Scanning held statements* for probable-duplicate pairs (FR-PD-9): runs the same rule over the stored statements, writes pair rows with their comparisons and the proposed kept copy, excludes pairs already dismissed and files the user overrode or removed. Can also run in a compute-only mode that writes nothing (used by the Backfill Tool).
  5. Reads the three detection settings (on/off, match ratio, small-statement minimum). When detection is off, nothing in 2–4 runs.
- **Interfaces**: Called by the Ingestion Orchestrator (judging and recording a skip), by `poll_once()` (the scan, a new branch), and by the Backfill Tool (compute-only scan, pre-registration). Depends only on the Shared Data Store and the Account Resolver's pure normalizer; makes no external calls.
- **Stories covered**: US-14.1, US-14.2 (snapshot selection), US-14.5 (finding pairs), US-14.7 (shared with the backfill)
- **Amendment (2026-10-04, Ingestion Worker Functional Design Question 1 = C)**: the detector also decides **whether removal may be offered** for a held pair and stores it on the pair (`removal_allowed`): true only when the two statements are of comparable size (the smaller has at least the match ratio times the larger's transactions). A pair of clearly different sizes is listed for information only. The worker computes it, the API displays it and never recomputes it, and the Statement Removal Handler re-verifies it. Ingestion still skips a probable duplicate of a different size, with the difference stated prominently; the Backfill Tool's reingest does not.

### Statement Removal Handler Component
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)**
- **Purpose**: Carry out a removal the user confirmed. The only code that deletes a statement, and the only way embeddings are removed, because the API Service cannot reach the vector store (NFR-PD-4).
- **Responsibilities**: Claim a pending removal job; **re-verify** it against what the user confirmed (the statement to remove still exists; its manual-correction count is not higher than the count the user acknowledged) and fail with a reason if not; in **one database transaction** delete the statement, its statement-account rows, its transactions, and every row depending on them, using the same dependent-row order the Backfill Tool's wipe uses, scoped to this one statement (one shared helper, moved out of the backfill rather than copied); record the removed transactions' ids on the job; commit; **then** delete those transactions' embeddings through the Vector Store Client; record the removed file's content hash as a **confirmed duplicate** (FR-PD-13); mark the pair removed; and report pending, then done or failed with a reason (FR-PD-14, NFR-PD-3). Ordering is deliberate: if the database step fails nothing is deleted; if the vector step fails after the commit, the job stays "embeddings pending" and is retried (bounded), leaving only harmless orphaned vectors — never a deleted vector beside a surviving row.
- **Interfaces**: Invoked by `poll_once()` only. Depends on the Shared Data Store and the Vector Store Client Component; never invoked by the API Service.
- **Stories covered**: US-14.6, US-14.4 (the removed copy is remembered)

### Account Resolver Component
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13, see `account-balance-application-design-plan.md`)**
- **Purpose**: Decide which account an extracted statement belongs to, creating the account if it is new.
- **Responsibilities**: From a statement's extracted bank name and account identifier, find the existing account for that pair or create a new one (FR-AB-1, FR-AB-2, US-13.1); when no identifier was extracted, fall back to an account keyed on the normalized bank name alone (A-2); carry the extracted account type onto a new account, leaving it unknown when it could not be determined (A-3); never silently overwrite a type or name the user has corrected through the Account Management Component (exact rule is Functional Design). Credit-card statements still resolve to an account — their transactions ingest exactly as today — but a non-deposit account never takes part in balances (FR-AB-4, NFR-AB-8).
- **Interfaces**: Called by the Ingestion Orchestrator Component after extraction succeeds and before the statement is recorded. Reads/writes accounts via the Shared Data Store; makes no external calls.
- **Stories covered**: US-13.1
- **Addendum (2026-10-02, found at Database Functional Design — BR-30, BR-31, BR-34)**: Resolves a statement by looking up its (`bank_key`, `account_identifier`, `currency`) in the new `AccountKey` entity rather than by matching on `Account` directly; the key includes the statement's currency (refining FR-AB-2), and the identifier is stored as printed on the statement, normalized only for spacing and hyphens (Question 1 = B). While `Account.type_user_set` is true it must never change the account's type.
  - **Scope change (2026-10-03)**: runs **once per account section** of a statement. Two sections of the same PDF that resolve to the same key are the same account and collapse into one section (a conflicting closing balance for the same account within one statement keeps the first and logs a warning).

### Categorization Engine Component (pluggable — Question 3 = A)
- **Purpose**: Assign a whitelist category (or `UNSURE`) to a transaction.
- **Responsibilities**: Defines a `CategorizationStrategy` interface with two concrete strategies — **Similarity Matcher** (fuzzy-matches against past transactions, prioritizing manually-corrected precedent per FR-5.3) and **LLM Classifier** (fallback, constrained to the whitelist). Orchestrates the fallback chain (similarity → LLM → UNSURE) per FR-5.2. Also handles the retroactive re-scan of existing `UNSURE` transactions triggered by a manual correction (FR-5.4), invoked via an async job from the API Service.
- **Stories covered**: US-2.1, US-2.2, US-2.3, US-3.4 (retro edge case)
- **Addendum (2026-08-02, Recategorization Review Panel feature)**: The retroactive re-scan (FR-5.4) is broadened and now split in two — searching `UNSURE` transactions *and* already-categorized transactions (US-6.1); auto-applying only very-high-confidence `UNSURE` matches as before (US-6.2), and always creating a pending proposal row (consumed by the new Recategorization Review Component) for everything else, including *every* match against an already-categorized transaction regardless of score (US-6.3). No new external dependency — reuses the existing similarity matcher.
- **Addendum (2026-08-08, Recurring Payments feature — Epic 8)**: Its similarity matcher gains a second caller — the new Recurring Payment Manager Component (below) — for matching a newly-persisted transaction against active Recurring Payments. No logic change to the Categorization Engine itself; this is purely a new call site (NFR-1).
- **Addendum (2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9, see `embedding-similarity-application-design-plan.md`)**: The Similarity Matcher strategy now tries embedding-based candidate search first (via the new Vector Store Client Component), falling back to the existing fuzzy-text approach only when no candidate clears the embedding-similarity threshold (FR-3, US-9.2) — the fuzzy-text matcher itself, including WR-20's normalization, is unchanged. Applies to both `categorize()` and `recategorizeUnsureFromPrecedent()` (FR-4). The existing amount-range gate and manual-source-precedence rule (WR-3) apply identically regardless of which method found the candidate (FR-5, NFR-1, US-9.3) — no separate, weaker check for the embedding path.
- **Addendum (2026-08-16, Matching Precision Refinement feature — see `matching-precision-refinement-application-design-plan.md`)**: The LLM Classifier strategy is no longer fallback-only — every transaction is classified by it (FR-MPR-1), via a new upfront, concurrent, per-file batch step (`classifyBatch`, Key Design Resolution 2) rather than a last-resort call inside `categorize()`. `categorize()`'s decision now combines the already-known LLM classification with similarity matching (FR-MPR-6): agreement auto-assigns as before; one confident signal with the other abstaining/absent auto-assigns the confident one directly; both confident and differing is a genuine disagreement, recorded as a new `CategorizationDisagreement` (Key Design Resolution 1) instead of a silent `UNSURE`. The embedded text for both this component's Vector Store Client calls and the Recurring Payment Manager's now includes a price-range bucket (FR-MPR-4), `embedding_similarity_threshold` is raised (FR-MPR-8), and candidate scoring gets a small boost when a candidate's known category agrees with the transaction's own LLM classification (FR-MPR-7) — exact per-call-site boost mechanics deferred to Functional Design (Design Decision 4). Each transaction's own LLM classification is now persisted (`Transaction.llm_suggested_category_id`, Key Design Resolution 3) so the retroactive re-scan can read it back later.
- **Addendum (2026-08-17, Categorization Model Fine-Tuning feature — see `categorization-model-finetuning-application-design-plan.md`, FR-CFT-9)**: The LLM Classifier strategy's prompt (both `classify` and `classifyBatch`) now also includes the transaction's `converted_amount_sgd` alongside `description` — so the live prompt shape matches what the new Model Training unit's Dataset Curator produces, keeping the fine-tuned model's training input and its real inference input identical. Bank name is deliberately excluded ("a very weak signal," per Resolved Decision 5). No change to the fallback chain, whitelist constraint, or `UNSURE` behavior.

### Currency Conversion Component
- **Purpose**: Compute a converted SGD amount for each transaction.
- **Responsibilities**: Fetch/cache historical FX rates per currency-pair/date from a public FX API; apply nearest-prior-date fallback when the exact date is unavailable and flag the result as approximate; leave a transaction unconverted (but still visible with its original amount) when no rate can be found at all.
- **Stories covered**: US-3.7, US-4.6

### Recurring Payment Manager Component
- **Addendum (2026-08-08, Recurring Payments feature — Epic 8, see `recurring-payments-application-design-plan.md`)**
- **Purpose**: Owns matching newly-ingested transactions against the Recurring Payments register, the review/trust/tolerance state progression, and periodic detection of untracked recurring charges.
- **Responsibilities**: Match a just-persisted transaction against active, unresolved-this-cycle Recurring Payments (reusing the Categorization Engine's similarity matcher, description/category + due-date window, amount as a loose guide per FR-5); create a pending match for a never-yet-approved Recurring Payment (FR-6), or auto-apply for a trusted one when the amount is within tolerance, else still create a pending match (FR-7); periodically scan transaction history for monthly-cadence repeating charges not yet covered by any Recurring Payment and record detection suggestions, respecting prior dismissals (FR-12/FR-13).
- **Stories covered**: US-8.4, US-8.5, US-8.6
- **Addendum (2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9)**: `matchNewTransaction` and `runDetectionScan` both gain the same embedding-first-then-fuzzy-fallback behavior as the Categorization Engine (FR-4, US-9.2), via the new Vector Store Client Component — matching against a Recurring Payment's `name` (not another transaction, a separate vector-store collection). - **Addendum (2026-08-16, Matching Precision Refinement feature — see `matching-precision-refinement-application-design-plan.md`)**: The embedded text used by both methods' vector-store lookups now includes a price-range bucket (FR-MPR-4), and candidate scoring gets a small boost when a candidate's known category agrees with the newly-ingested transaction's own LLM classification, computed by the Categorization Engine's new batch-classification step (FR-MPR-7) — no disagreement-review branch here (Design Decision, FR-MPR-12: recurring-payment matching has no per-transaction category-assignment decision to disagree over). Exact boost mechanics per call site deferred to Functional Design.

### Vector Store Client Component
- **Addendum (2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9, see `embedding-similarity-application-design-plan.md`)**
- **Purpose**: All interaction with the vector database — the Drive Connector Component's equivalent role for embeddings.
- **Responsibilities**: Store an embedding vector for a transaction description or a Recurring Payment name (two logical collections); query nearest neighbors by cosine similarity, given a vector, a target collection, and result-filtering criteria (e.g. excluding the source transaction itself). Shared by the Categorization Engine, Recurring Payment Manager, and the Embedding Manager Component below — no other component talks to the vector DB directly.
- **Stories covered**: US-9.2 (as the mechanism enabling embedding-based candidate search)
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14)**: Gains its first **delete** operation — remove the embeddings of a list of transactions from the `transactions` collection, by id (FR-PD-12). Idempotent: an id that is not present is not an error, so a retried removal is safe. Only the new Statement Removal Handler calls it. (The Backfill Tool's whole-collection recreate is a different, existing operation.)

### Embedding Manager Component
- **Addendum (2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9, see `embedding-similarity-application-design-plan.md`)**
- **Purpose**: Owns *when* a transaction's own embedding gets computed and persisted — a time/backlog-triggered concern, distinct from the query-time embedding computation the Categorization Engine and Recurring Payment Manager perform for themselves via the Vector Store Client (see the plan doc's "Key Design Resolution").
- **Responsibilities**: Call the user-managed oMLX endpoint (config-supplied base URL) to compute an embedding for a transaction's raw description (FR-9: no pre-normalization); store it via the Vector Store Client and update the transaction's `embedding_status`; process a bounded batch of pending transactions per poll cycle — this single mechanism serves both newly-ingested transactions (FR-6) and the one-time historical backfill (FR-11), since both are just "transactions with `embedding_status = pending`." Soft-fails per transaction/batch when the endpoint is unreachable (FR-10) — never blocks or fails an ingestion run.
- **Stories covered**: US-9.1, US-9.4, US-9.5
- **Addendum (2026-08-12, retroactively during Ingestion Worker Service Functional Design — see `ingestion-worker-embedding-similarity-functional-design-plan.md` and audit.md)**: The pending-backlog this component drains is not transactions-only. `RecurringPayment` rows also carry an `embedding_status` (Database `BR-25`, added retroactively at this stage) — the API Service's Recurring Payments Component sets it to `pending` on create or on any `name`-changing update, since API Service never calls the embedding endpoint/vector store itself. `processNextEmbeddingBatch()` drains both entity types' `pending` backlogs (one unified mechanism, per this component's original design principle) — see `services.md`'s corresponding addendum for the updated `poll_once()` due-check.

### Ingestion Orchestrator Component
- **Purpose**: The Worker Service's coordination layer — the only component that calls the others in sequence.
- **Responsibilities**: Pick up a queued run request; for each file: Drive Connector download → Duplicate Detection check → (if new) Statement Extraction → Categorization Engine → Currency Conversion → persist transactions; update run/file-level progress and status continuously so the API Service's polling reflects near-live state; ensure one file's failure doesn't abort the run (NFR-2.2).
- **Stories covered**: US-1.2, US-1.5 (progress/history data producer)
- **Addendum (2026-10-02, Account Balance at a Point in Time feature — Epic 13)**: The per-file sequence gains the Account Resolver Component between Statement Extraction and recording the processed statement: Drive download → Duplicate Detection check → Statement Extraction → **Account Resolver** → record processed statement (now carrying account reference and closing balance) → Categorization Engine → Currency Conversion → persist transactions. A file whose extraction fails still never reaches the resolver, so no account is ever created from a failed extraction. This per-file sequence is also what the Backfill Tool Component reuses for its reingest — the same code path, not a copy.
  - **Scope change (2026-10-03)**: the Account Resolver step becomes a loop over the statement's account sections, and conversion, classification (still one batch per file), and persistence carry each transaction's section currency and section link.
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14)**: The per-file sequence gains two checks, with no new method: **before extraction**, after the exact-bytes check, the remembered-file lookup (Duplicate Detection Component) decides skip / proceed; **after extraction succeeds and before the Account Resolver**, when detection is on and the file was not overridden, the Probable Duplicate Detector judges the extracted statement against the held ones and, on a probable duplicate, records the skip and marks the file with the new skipped-probable-duplicate outcome. Placing the second check before account resolution is what guarantees a skipped file creates no account, section, or transaction (FR-PD-1). A skip is not a failure: it does not abort the run, and the per-file SAVEPOINT is untouched.

## Backfill Tool (new, 2026-10-02, Account Balance at a Point in Time feature — Epic 13, see `account-balance-application-design-plan.md`)

Architecturally like Model Training's entry points, not like the services above: no docker-compose service of its own, no persistent process, no polling loop, no REST endpoints, no UI (Question 2 = A). A single command-line entry point shipped in the Ingestion Worker Service's package and image, run manually via `docker compose`, because it needs exactly what that service already has — Drive access, the extraction pipeline, and the shared database package.

### Backfill Tool Component
- **Purpose**: The one-time, safety-gated wipe-and-reingest that gives every existing statement an account, an account type, and a closing balance.
- **Responsibilities** (US-13.7, FR-AB-15/16/17, NFR-AB-2): print a dry-run report (statements, transactions, manual corrections, and dependent rows that would be affected) changing nothing; take and verify a backup of the affected data and report its location; require an explicit typed confirmation before any wipe; capture manual category corrections (`category_source = manual`) keyed by statement content hash, transaction date, amount, and description; wipe statements, transactions, and the rows that depend on them; reingest every PDF from Drive **in-process through the Ingestion Orchestrator Component's normal per-file sequence**; re-apply captured corrections best-effort by that key; print a completion report listing each unmatched correction individually, each PDF that failed to reingest with its reason, the count of recurring-payment matches re-derived by ingestion-time matching, and which kinds of dependent rows were discarded.
- **Interfaces**: Command-line only. Depends on the Shared Data Store, the Drive Connector Component, and the Ingestion Orchestrator's per-file sequence. The correction-matching helper lives here, not in the shared pipeline.
- **Constraints handed to Functional Design** (not decided here):
  1. **No concurrent runs.** The Ingestion Worker's own poll loop processes one run at a time; the tool must not interleave with a normal ingestion run. Whether it checks for idle, takes a lock, or requires the worker to be stopped is a Functional Design decision.
  2. **Backup mechanism.** The existing nightly backup (Backup Manager Component) snapshots only the `transactions` table as CSV into Drive; the worker image has no `pg_dump` and no host-mounted output directory. The pre-wipe backup must cover more than transactions (statements, proposals, jobs, disagreements, matches), so Functional Design must pick a mechanism — and **may reopen Infrastructure Design**, which the execution plan skipped on the condition that no new runtime path was needed.
- **Stories covered**: US-13.7
- **Addendum (2026-10-02, found at Database Functional Design — BR-36)**: Three further constraints for Ingestion Worker Functional Design. (3) **Vector-store cleanup**: wiping transactions leaves their embedding vectors in the vector store keyed by now-deleted transaction ids, and the Vector Store Client Component has no delete operation today — the tool must remove them as part of the wipe, so the retroactive re-scan cannot match against ghosts. (4) **Wipe set**: `recurring_payment_matches`, `categorization_disagreements`, `recategorization_proposals`, `recategorization_jobs`, `transactions`, `statement_accounts`, `bank_statements`, in that order, after detaching `ingestion_run_files.bank_statement_id`; `accounts`, `account_keys`, and `balance_anchors` are never wiped, so a re-run keeps every merge, rename, type, and anchor. (5) **Keys carry the merge forward**: reingested statements resolve through the kept `account_keys` to the same accounts, so anchors apply immediately.
- **Addendum (2026-10-03, Ingestion Worker Functional Design — see `ingestion-worker-account-balance-functional-design-plan.md`, WR-52..WR-56)**: Constraints 1 and 2 above are resolved. (1) **No concurrent runs**: the tool refuses while any run or job is queued or running, and its own reingest holds the single active-run slot, so no normal run can start meanwhile. (2) **Backup**: a Python export of every table the wipe touches, as JSON-lines files plus a checksummed manifest, uploaded to a timestamped subfolder of the existing Drive `backup` folder, **downloaded back and verified** before anything is wiped, with a `restore` command; no image or compose change, so **Infrastructure Design stays skipped**. The tool has three commands (`run`, `finish --backup`, `restore --backup`); the wipe set is statements that have no account sections yet **and** whose PDF is still in Drive; `finish` re-applies manual corrections from the backup artifact and writes the completion report.
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)**: The tool gains duplicate handling so the reingest resolves the existing pairs instead of recreating them (US-14.7, Q7 = A, FR-PD-18). (1) A new **read-only `check-duplicates` command** runs the Probable Duplicate Detector in compute-only mode over the stored statements and prints each pair found, the verdict's reason, and the copy that would be kept — the NFR-PD-1 accuracy gate and the source of the dry-run listing. (2) The **dry run lists** the pairs it will skip and which copy it keeps (FR-PD-15). (3) `run` **pre-registers** each pair's copy-to-skip as a remembered probable duplicate, by content hash, pointing at the kept copy and reusing the pair's comparison, immediately before the reingest; the reingest's ordinary pre-extraction lookup then skips it deterministically, in any file order, with no Gemini call (FR-PD-16). A remembered probable duplicate is never re-evaluated, which is what makes this independent of the order files are processed. (4) `finish` carries manual corrections captured from **every** file skipped as a probable duplicate during the reingest — pre-registered or flagged inline — onto the matching transactions of the kept copy, using the remembered record's matched hash, instead of reporting them unmatched (FR-PD-17). (5) The completion report lists the skipped duplicates and the corrections carried. (6) Pairs the user dismissed are honoured (not skipped, not listed). (7) The tool's backup/restore and its refusal-while-busy check extend to the new tables and the removal and scan work. Detail is Ingestion Worker Functional Design.

No per-statement account type is stored. See `construction/database/functional-design/`.

A fourth entity, `statement_accounts` (one row per account per statement: the statement, the account, and the account's closing balance and date, together or not at all), carries them, and `transactions` gains a link to its `statement_accounts` row, guaranteed by the schema to belong to the transaction's own statement.
- **Addendum (2026-10-03, Probable Duplicate Statement Detection feature — Epic 14, see `probable-duplicate-application-design-plan.md`)**: Five new entities and one enum value. (1) **Remembered files** — one row per content hash with a state (probable duplicate / overridden / confirmed duplicate), the matched statement's content hash, and a link to the comparison; written by four parties (the Probable Duplicate Detector on a skip, the Duplicate Review Component on an override, the Statement Removal Handler on a removal, the Backfill Tool on pre-registration), read by the Duplicate Detection Component before extraction. (2) **Comparisons** — the stored snapshot of both sides (labels, periods, counts, matched count, up to 10 marked transactions each), self-contained so it survives the original being changed or removed (US-14.2). (3) **Duplicate pairs** — pairs found among the held statements, referring to the two statements **by content hash, not row id**, with status (pending / dismissed / removal requested / removed), the comparison, and the proposed kept copy; written by the worker's scan, status-updated by the Duplicate Review Component. (4) **Removal jobs** — written by the Duplicate Review Component, executed by the Statement Removal Handler; hold the removed transactions' ids until their embeddings are confirmed deleted. (5) **Scan state** — when a scan last ran and against which settings, and a re-check request. `IngestionRunFileOutcome` gains **skipped as a probable duplicate**, and `ingestion_run_files` gains a link to the comparison. Keying by content hash is what lets these records stay valid across the Account Balance backfill, which recreates every statement with a new id. Exact shapes, constraints, and migration are a Functional Design (Database unit) decision.
  - **Resolved at Database Functional Design (2026-10-03, see `database-probable-duplicate-functional-design-plan.md`, BR-39..BR-52)**: **six** entities, not five — the comparison's rows (up to 10 per side) are a child table, `duplicate_comparison_rows`, rather than a stored list, so the database itself enforces the 10-row bound and the project stays free of JSON columns. The comparison's two sides are named **earlier** (the original) and **later**, which works for both a skipped file and a held pair. Pairs are unordered and unique by their two hashes, carry the worker's stored keep-proposal, and have the statuses pending / dismissed / removed / superseded (the backfill marks resolved pairs `superseded` rather than deleting them). A remembered file can be overridden from either `probable_duplicate` or `confirmed_duplicate`, so a wrongly removed copy has an in-app way back. A guard test over the table metadata fails if any table outside the known list gains a foreign key to `transactions`, `statement_accounts`, or `bank_statements`. None of the six has such a key.

### Vector Store (new, 2026-08-11, Local Embedding-Based Semantic Similarity feature — Epic 9)
- A **separate, dedicated vector database service** (product TBD at NFR Requirements) — not part of the PostgreSQL-class Shared Data Store above. Holds two logical collections: transaction-description embeddings and recurring-payment-name embeddings.
- Written to and queried **only by the Ingestion Worker Service**, via the new Vector Store Client Component. The API Service never connects to it directly — consistent with this project's "no direct API-Service-to-Worker-owned-thing" pattern (same as `backup_runs`, recategorization proposals, etc., which the API Service only ever reads via its own Postgres connection, never by reaching into a Worker-owned datastore).
