# Application Design Plan — Probable Duplicate Statement Detection (Epic 14)

**Role**: Software architect, identifying components/methods/services/dependencies for Epic 14.

## Design decisions made and explained (not asked), with reasoning

Each follows from the approved requirements, stories, and this project's established conventions, and has one defensible answer. Two are called out at the bottom because they deserve your eyes at approval even though they are not open questions.

| Category | Decision | Why this isn't a question |
|---|---|---|
| **Component identification (Ingestion Worker)** | A new **Duplicate Detector Component** (own package, `duplicates/`) holding (a) the pure matching rule (match ratio, period overlap, small-statement exclusion, comparison-snapshot selection: the property-testable core, NFR-PD-7) and (b) the database-facing steps: judge an extracted statement against the held ones, and find probable-duplicate pairs among held statements. The existing **Duplicate Detection Component** (the byte checksum) stays as it is and gains one step: look up the **remembered record** for a file's content hash before extraction. | Matches the project's habit of small single-purpose components called by the orchestrator (Duplicate Detection, Currency Conversion, the Account Resolver). The checksum check and the content-similarity check are different mechanisms with different inputs (bytes before extraction versus extracted transactions after), so they are separate components. |
| **Where the check runs in the pipeline** | Two points in the per-file flow: **before extraction**, after the exact-checksum check, the remembered record for the file's hash is consulted (skip, or proceed because the user overrode it, FR-PD-8/13/7); **after extraction and before the Account Resolver**, the extracted statement is judged against the held ones (FR-PD-1), so a skipped file creates no account or section. | Both placements are forced by the requirements: remembering by hash exists precisely to avoid a Gemini call (NFR-PD-2), and detecting before account resolution exists precisely so nothing is created from a skipped file. |
| **Remembered records and comparisons are data, not code** | Two new entities. A **remembered file** keyed by content hash with a state (`probable_duplicate`, `overridden`, `confirmed_duplicate`), the hash of the statement it matched, and a link to its comparison. A **comparison** holding the two sides' headline figures and up-to-10-transaction snapshots (FR-PD-5). A **probable-duplicate pair** entity (status pending/dismissed/removed) for duplicates already ingested. Matched statements are referred to **by content hash, not by row id**. | The skipped file's transactions exist nowhere else, so they have to be stored (FR-PD-5). Referring to statements by content hash is what lets these records survive the Account Balance backfill, which deletes and recreates every statement with new ids; it is also what lets a dismissal or an override stay valid after a restore. |
| **Existing pairs are found by the worker, read by the API** | The Ingestion Worker scans the held statements with the same matcher and writes the pair rows; the API Service only reads them and records the user's decisions. The scan runs when none has ever run and whenever a detection setting changes, and on a "check again" request row the user can create from the panel. It is **one more branch in the worker's existing poll loop**, after the existing ones. | The API Service must not duplicate the matching algorithm (two copies would drift) and has no business computing it per request; the worker already owns every "find things in the history" scan (the recurring-payment detection scan is the direct precedent). New duplicates cannot arise from ingestion (they are skipped), so pairs only come from data that was already there, which is why a scan on enable and on a setting change is enough. |
| **Removal is a job the worker performs** | Confirming a removal in the app writes a **removal job** row; the worker performs it in one transaction (the statement, its sections, its transactions, and everything depending on them, scoped to that one statement), then deletes the transactions' embeddings, then records the removed copy's hash as `confirmed_duplicate`, and reports pending/done/failed (FR-PD-12/13/14). The vector store client gains a **per-point delete** (today it can only upsert and query). | The project's one hard architectural rule: the API Service never connects to the vector store, and the two services coordinate only through shared rows (NFR-PD-4). The job pattern is the established way to do this (recategorization jobs). The database deletion commits first and the embeddings are deleted after, so a failure leaves harmless orphaned vectors that are retried, never a deleted vector beside a surviving row. |
| **The API Service's side** | A new **Duplicate Review Component**: list pairs and their count (for the badge), the comparison view, confirm removal (writes the job), dismiss a pair, override a skipped file ("ingest it anyway", writes the remembered record). The existing **Ingestion Trigger & Status Component**'s run-file DTO gains the skip's label and comparison id. | Matches the project's granularity (Recategorization Review, Backup Status, and Recurring Payments are each their own component), and reuses the existing pending-count pattern for the badge. |
| **The Frontend** | Extend the single **Frontend SPA** component's responsibilities: a panel on the Review page, a badge beside the existing Review badge, the comparison view shared by both entry points (the Ingestion results link and the Review panel), and the override action. | `components.md` already treats the whole SPA as one component with every page a responsibility of it. A single shared comparison view keeps the two entry points consistent. |
| **Settings** | Three settings on the existing Settings page, owned by the worker: the **match ratio** (default 0.80), the **small-statement minimum** (default 3), and an **on/off switch** for detection (also gates the pair scan). | The project already exposes tunables this way (44 settings today); Q2 and Q3 chose values that are exactly these tunables; and the switch is the safety valve the Workflow Plan promised. |
| **The accuracy gate has a command** | The Backfill Tool gains a **read-only `check-duplicates`** command that runs the matcher over the held statements and prints the pairs it finds. It is both the NFR-PD-1 acceptance check and the source of the backfill's dry-run listing (FR-PD-15). | NFR-PD-1 makes accuracy on the real statements a gate, which needs a way to run the matcher read-only on them; the existing `check-extraction` command is the direct precedent, and the Requirements' open item on a preview command resolves to yes. |
| **The backfill resolves duplicates by pre-registering the skips** | The backfill's `run` records, in the backup manifest, each pair it found and which copy the Q6 rule keeps; just before the reingest it creates a `probable_duplicate` remembered record for the **other** copy's content hash, pointing at the kept copy's hash. The reingest's normal pre-extraction hash check then skips that file deterministically, in any order, with no Gemini call; `finish` maps each manual correction captured from a skipped copy onto the kept copy's matching transactions (FR-PD-16/17). | Pre-registering by hash needs no new ordering logic and no new pipeline mode (the pipeline already consults remembered records, above), it cannot depend on which Drive file happens to be listed first, and it keeps the corrections-on-the-skipped-copy case (true of both of your pairs) from being reported as unmatched. |
| **Overrides and dismissals are never re-flagged** | A file the user overrode and a pair the user dismissed are excluded from the pair scan, by content hash. Without this, an overridden file would be ingested, then found by the scan as a duplicate pair, then offered for removal again. | A direct consequence of FR-PD-7 and A-PD-5: the user said these are not duplicates. |
| **Default state of detection** | **Off** when first deployed. It is turned on only after the accuracy evaluation (`check-duplicates`) shows the NFR-PD-1 result, as part of Build and Test with your go-ahead. | NFR-PD-1 states the feature is enabled only after that evaluation; shipping it on would enable it before evidence exists. |
| **Dependencies** | New API Service and Ingestion Worker components depend only on the Shared Data Store; no new edge between the two services; no new external call. | The project's one hard rule (DB-only coordination). |
| **Interface style** | Plain REST resources under a new router, matching existing conventions; paths and DTOs are Functional Design. | One consistent API style already exists. |

### Two decisions to look at when you approve

1. **Detection ships switched off** and is turned on after the accuracy check. The cost is that duplicates keep arriving until you (or Build and Test, with your go-ahead) switch it on; the benefit is that it is never enabled blind.
2. **Everything remembered is keyed by content hash**, including the match target, so these records stay valid across the Account Balance backfill and a restore. The cost is that they reference a statement by hash rather than by a database link, so the app resolves that reference when it reads.
