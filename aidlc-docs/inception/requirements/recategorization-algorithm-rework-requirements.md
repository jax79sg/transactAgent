# Recategorization Algorithm Rework — Requirements

## Intent Analysis Summary

- **User request**: "the recategorisaion scan is a total failure. we need to totally rework on the algorithm."
- **Request type**: Enhancement/Rework — replacing existing matching logic in an existing feature due to a real, evidence-confirmed accuracy problem.
- **Scope estimate**: Single Component (Ingestion Worker Service's Categorization Engine — the retroactive re-scan's matching algorithm is the primary target; the shared embedding-text construction it and two other consumers depend on is also in scope, at the user's explicit direction — see Background item 4).
- **Complexity estimate**: Moderate, narrowed from the original scope (changes the re-scan's precedent-pool strategy and reworks a shared embedding-text builder used by two other consumers; the LLM verification step originally planned is deferred — see FR-RAR-2 — so this is now a pure embedding-accuracy improvement, not an algorithm-plus-verification-layer change; no new component, no new service).

## Background (from live evidence + code research)

The "recategorization scan" is `recategorize_unsure_from_precedent` (`ingestion-worker/src/ingestion_worker/categorization/service.py`) — triggered whenever a transaction is manually corrected, it scans existing `UNSURE` transactions for matches against that one just-corrected transaction, auto-applying above a high-confidence threshold or creating a `PENDING` proposal for manual review otherwise.

**Evidence gathered before writing this document** (queried the live `recategorization_jobs`/`recategorization_proposals`/`categorization_disagreements` tables):

1. **Confirmed failure, dated**: Every proposal batch from 2026-08-23 through 2026-08-27 was rejected (100%, ~9 jobs) — a sharp change from the healthy approve/reject/auto-apply mix seen 2026-08-15–08-18.
2. **Root cause is structural, not a config value**: Rejected proposals' match scores cluster almost entirely in the 75-83 range. The live `.env` overrides `EMBEDDING_SIMILARITY_THRESHOLD=0.75` (looser than `config.py`'s coded default of `0.82`), but most rejected matches score *above* 0.82 too — reverting the override would not have prevented the majority of these. The real cause: Singapore PayNow transfer descriptions are dominated by boilerplate phrasing (`"FAST PAYMENT via PayNow-UEN to ... OTHR - ..."`), so two transactions to completely unrelated payees (e.g. `HITPAY PAYMENTS`, `NOVALAND PTE LTD`, `Askalamoonzxs`, `REVIN TANRI`) score 75-83 on embedding similarity purely from shared boilerplate — comfortably clearing the pending-proposal bar despite having nothing to do with each other. Real examples pulled from the rejected batch: unrelated PayNow transfers to `HITPAY PAYMENTS`, `NOVALAND PTE. LTD`, `Askalamoonzxs`, and `REVIN TANRI` were all cross-proposed against each other as `Transfer`/`Claims`/`Gift`/`Household`/`Maid`.
3. **Ingestion-time categorization (`categorize()`) investigated and confirmed NOT to show the same pattern** (User Answer Q2): `categorization_disagreements` has zero rows since 2026-08-15, and a spot-check of ~20 recent PayNow-boilerplate transactions categorized via `categorize()`'s `similarity` source shows substantively correct categories (e.g. Qashier-prefixed PayNow transfers, a common F&B point-of-sale system, correctly landing as `Dining`). The likely reason: `categorize()` already does a full nearest-neighbor search across *all* precedent transactions (`find_similar_transaction_via_embedding`, via the `transactions` vector-store collection) plus an always-on independent LLM classification that must agree before an assignment is made — the re-scan does neither. It only does a single pairwise comparison against the *one* transaction that was just corrected, with no LLM cross-check at all (by original design, WR-5, to keep the re-scan cheap).
4. **Embedding text construction itself was raised by the user as a second, related angle** (follow-up feedback during requirements review): `build_embedding_text` (`ingestion-worker/src/ingestion_worker/embedding/text.py:32`) is a single shared function — `f"{description} | {price_bucket_label(amount)}"`, raw description plus a price bucket, nothing else — used by three consumers: the re-scan, `categorize()`, and Recurring Payment Manager's own matching (`recurring_payments/service.py`), plus the async storage-time embedding batch (`embedding/service.py`) that persists vectors for all of them. It carries no in-flow/out-flow direction signal, and reference codes/transaction IDs inside the raw description are embedded with the same weight as the actual payee name — directly consistent with the boilerplate-noise root cause in item 2 above.

This confirms the user's instinct: the re-scan's core matching *design* — not a tunable threshold — needs to change, and it should borrow the two properties that already make ingestion-time categorization reliable: a broader precedent pool, and an independent LLM check. The user separately asked to revisit the shared embedding construction itself; see FR-RAR-6.

## Functional Requirements

- **FR-RAR-1 (Broaden the precedent pool)**: The re-scan must stop comparing each `UNSURE` transaction against only the single just-corrected transaction. It must instead search against the fuller pool of precedent transactions relevant to the category being corrected (User Answer Q3) — mirroring the multi-candidate nearest-neighbor approach `categorize()` already uses at ingestion time, rather than one pairwise cosine check. Exact retrieval mechanism (vector-store query vs. DB-side candidate set) is a Functional Design decision.
- **FR-RAR-2 (LLM verification step — DEFERRED, not in scope for this rework)**: Originally planned (User Answer Q4 of the first round) as an independent LLM classification cross-check before any auto-apply/proposal. **Superseded**: the user decided to focus this rework purely on embedding accuracy and explicitly excluded LLM involvement in recategorization "for now" (User Answer, second Request Changes round). Kept documented here as a deferred future enhancement (User Answer Q2=B of the `no-llm-questions.md` round) rather than deleted outright — if the embedding-accuracy improvements below (FR-RAR-1, FR-RAR-6, FR-RAR-7) don't sufficiently reduce false positives on their own, this is the next lever to pull. Not designed or built in this pass.
- **FR-RAR-3 (Precision-first tuning)**: The reworked algorithm's thresholds/scoring must be tuned to minimize false-positive proposals and auto-applies, accepting more transactions being left `UNSURE` (i.e. no match forced) as the tradeoff (User Answers Q1 [A+C — both bad matches surfacing and real matches being missed are live problems] and Q6 [A — precision preferred over auto-apply coverage]). With FR-RAR-2 deferred, this tuning plus the embedding-accuracy improvements (FR-RAR-1, FR-RAR-6, FR-RAR-7) are now the *only* levers for precision in this pass — carries more weight than originally planned.
- **FR-RAR-4 (Scope boundary — confirmed, not assumed, refined by FR-RAR-6, narrowed by FR-RAR-2's deferral)**: The *matching-algorithm redesign* for this rework is now just the broader precedent pool (FR-RAR-1) — the independent LLM verification gate originally paired with it (FR-RAR-2) is deferred, not built now. `categorize()` (ingestion-time categorization) remains confirmed out of scope for the matching-algorithm redesign per the investigation above (User Answer Q2 asked this be checked before deciding). This boundary does NOT extend to the shared embedding-text construction changes (FR-RAR-6, FR-RAR-7), which the user explicitly chose to apply everywhere.
- **FR-RAR-5 (Reconcile the threshold divergence)**: The live `.env` value for `EMBEDDING_SIMILARITY_THRESHOLD` (0.75) diverges from `config.py`'s coded default (0.82) with no documented reason found. This rework must reconcile the two (either by design deliberately, with a documented reason, or by removing the override) rather than leaving an unexplained gap in place — understanding this is expected to be a minor contributor at most, not the primary fix (per the evidence in Background item 2).
- **FR-RAR-6 (Rework shared embedding-text construction, applied globally)**: `build_embedding_text` must be extended to include an in-flow/out-flow direction signal, appended as a token in the embedded text alongside the existing price-range bucket (e.g. in the style of `"... | $10 to $50 | outflow"`) — not as a separate hard pre-filter (User Answer Q2=A). This change applies to the function itself, so it takes effect for all three consumers: the re-scan, `categorize()`, and Recurring Payment Manager (User Answer Q1=A — deliberately broadened beyond the re-scan, a single shared fix rather than a re-scan-only fork of the function).
- **FR-RAR-7 (Strip reference-code/ID noise before embedding — reversed from the original decision)**: **Supersedes the original FR-RAR-7.** The original decision (User Answer Q3=B, embedding follow-up round) was to keep descriptions raw and rely on the LLM verification gate (FR-RAR-2) to catch reference-code-driven false matches. With FR-RAR-2 now deferred, that safety net doesn't exist, so the decision is reversed: obviously ID-like substrings (long alphanumeric reference codes, transaction reference numbers — e.g. the `DICNP17537901512105MMHTZ8`/`EPOSSPSPTWM8J GOJ IIFTRGNB`-style tokens seen in the boilerplate-noise evidence) must be stripped/scrubbed from the description before embedding (User Answer Q1=A, `no-llm-questions.md` round). Exact stripping heuristic (regex pattern, length/entropy threshold, etc.) is a Functional Design decision. Applied via the same shared embedding-text construction path as FR-RAR-6, so it takes effect for all three consumers (re-scan, `categorize()`, Recurring Payment Manager) — consistent with FR-RAR-6's established "one shared function, one fix" scope.

## Non-Functional Requirements

- **NFR-RAR-1 (Moot for this pass — LLM latency/cost only applies if/when FR-RAR-2 is built)**: Originally assessed the added latency/cost of a per-candidate LLM verification call as acceptable given the re-scan's low per-correction-event volume. Not applicable now that FR-RAR-2 is deferred; kept here for continuity if that future work is picked up.
- **NFR-RAR-2 (Historical data left alone, pending Functional Design confirmation)**: Following this project's established precedent (`recategorization-scope-narrowing-requirements.md`'s FR-RSN-3), existing `RecategorizationProposal` rows from before this rework are assumed left as-is, not backfilled or bulk-reprocessed — flagged here for explicit re-confirmation at Functional Design/Workflow Planning rather than silently assumed, since this wasn't directly asked in this round of questions.
- **NFR-RAR-3 (Stale-vector risk from the embedding-text format change — resolved at Functional Design)**: `process_next_embedding_batch` (`embedding/service.py`) only ever embeds rows in a `pending` state. Resolved: a full re-embedding backfill will run (WR-39, `business-rules.md`), following the exact precedent set by WR-32 when this same function's format last changed. Explicit constraint: the backfill touches embeddings/`embedding_status` only — assigned categories (`category_id`, `category_source`) must not change as a side effect.

## Summary

The retroactive recategorization re-scan currently only compares an `UNSURE` transaction against the single transaction that was just manually corrected, with no LLM cross-check — a design that works fine for distinctive descriptions but collapses for Singapore's boilerplate-heavy PayNow transfer descriptions, where unrelated payees can look 75-83% similar purely from shared payment-rail phrasing. Live evidence confirms this: 100% of proposals were rejected from 2026-08-23 through 2026-08-27, and the rejected matches' scores land almost entirely in that boilerplate-driven range — mostly above even the code's own stricter threshold, ruling out a simple config fix.

**Final scope, after two rounds of Request Changes during review**: this rework is now a pure embedding/matching-accuracy improvement, not an accuracy-plus-verification-layer change. In scope: (1) broaden the re-scan from a single-precedent pairwise comparison to a fuller precedent pool (FR-RAR-1); (2) rework the shared `build_embedding_text` — used by the re-scan, `categorize()`, and Recurring Payment Manager alike — to add an in-flow/out-flow signal (FR-RAR-6) and strip reference-code/ID noise before embedding (FR-RAR-7, reversed from the original raw-text decision now that there's no LLM safety net); (3) reconcile the `.env`/code threshold divergence (FR-RAR-5); (4) tune thresholds toward minimizing false positives, accepting more `UNSURE` outcomes as the tradeoff (FR-RAR-3). Explicitly deferred, not built now: the independent LLM verification gate (FR-RAR-2), kept documented as a future enhancement if embedding accuracy alone proves insufficient. `categorize()` remains out of scope for algorithm redesign (it already does a full-pool search) but inherits the embedding-text changes like every other consumer. NFR-RAR-3's stale-stored-vector risk from the text-format change still applies and still needs a Functional Design decision.
